## Why

Внешний консьюмер (плагин харнесса `caped-context`, adopting-репо) хочет реагировать на
события капеда: увидеть новую идею от соседнего агента, прислать промоут-гейт в сессию, когда
чейндж заархивирован. API для этого нет — консьюмеру пришлось бы парсить `git log` по трейлерам
или диффить содержимое `ideas/`/`changes/` на каждом шагу. Но события — это уже выводимые факты
тула (history строится из git-трейлеров): их обязан отдавать сам тул, а не реконструировать каждый
консьюмер. commit-msg хук — входная площадка дисциплины; нужен встречный канал: факт → событие
наружу.

## Context

- Капед уже умеет: history из git-трейлеров, `check push` (pre-push диапазон), хуки
  (`commit-msg`, планируемый `pre-push` шим из adhoc-verify), адхок-нормы (`Adhoc: <name>`).
  Лента событий — это тот же источник, что у history, но как поток с курсором, без парсинга формата
  трейлеров в консьюмере.
- Консьюмер сегодня: плагин `caped-context` читает реестр/идеи/чейнджи с диска на каждом шаге
  (live-состояние) и планирует инъекции по точкам решения (`reminder-timing`). События закрывают
  «увидел новую идею» и «заархивирован → промоут-гейт» без диффов.
- Связки: `reminder-timing` (триггеры инъекций = события), `multiagent-events` (кросс-агентные
  уведомления — события и есть их транспорт), `e2e-harness-realism` (тайминг инъекций виден по
  траекториям — лента даёт детерминированный вход).

## Requirements

- v0 = лайфцикл-события: idea born, taken into work, archived, adhoc committed + tool-updated (версия тула).
- Запись: post-commit шим от init (читает HEAD-трейлеры → событие) + самопроверка версии тула; commit-msg — гейт ДО.
- Лента: `.caped/events/feed.jsonl` (append-only, seq в строке, одна строка = один write(2), строки < PIPE_BUF) + `caped events --since <seq>`; один источник правды с history.
- Хук-дистрибуция в стиле git: `.caped/hooks/<event>` — версионированный каталог (НЕ гитигнорен), диспетчер запускает с env-контекстом; чейнджлог-реген = такой же хук.
- Версия-константа = голова встроенного чейнджлога (view `render changelog`, derived из contract-коммитов); автоген по событию архива/контракта (пост-коммит), файл игноренный в бандле; бинарь вшивает на сборке.
- Нотификация ≠ энфорсмент: события — факты ПОСЛЕ действий, хуки остаются гейтами ДО.
- Безопасность хуков: хуки = политика владельца репо (как git hooks, script-хуки в package.json) — принимается, документально.
- Интеграционный эскиз: плагин читает ленту по курсору или ставит собственный `.caped/hooks/<event>`.
- НЕ в v0 (точка расширения, отдельная идея при появлении потребителя): события состояний проверок (trace-red/check-red).

## Decisions

- Транспорт: `.caped/events/feed.jsonl` (append-only, seq, курсор = seq) + `caped events --since <seq>`; один источник правды с history.
- Пишущие: post-commit шим от init (события по трейлерам HEAD) + самопроверка версии тула (tool-updated); commit-msg остаётся гейтом ДО.
- Хук-дистрибуция: `.caped/hooks/<event>` (версионируется, не гитигнорен) — реакции на события живут как хуки, не в логике тула; chandжлог-реген = такой же хук.
- Версия-константа = голова встроенного чейнджлога; реген автоматически по событию архива/контракта (пост-коммит), файл игноренный в бандле; бинарь вшивает на сборке.
- Атомарность записей: одна строка = один `os.write(fd, …)` с `O_APPEND`, строки меньше PIPE_BUF.
- Чужие ленты не нужны: посылка между репо = коммит (идея-файл) в репо ПОЛУЧАТЕЛЯ; локальная лента достаточна.
- Безопасность хуков: хуки = политика владельца репо (как git hooks) — принято.
- Скоуп v0 (реализация 2026-08-23): лайфцикл-лента + дистрибуция — feed.jsonl, post-commit эмиттер, `caped events --since`, `.caped/hooks` диспатч, кап hooks в реестре, init-шим. tool-updated/встроенный чейнджлог/autoreген — фаза 2, депозитом в `_backlog`. События состояний проверок — вне v0 (депозит в `_backlog`). Ротация — O4 решён (обрезка по 1000).

## Rejected alternatives

- Парсинг git-истории в консьюмере — отвергнуто: дублирование формата трейлеров в каждом
  консьюмере, хрупко к эволюции; событие — работа тула.
- Поллинг-дифф файловой системы — отвергнут: шум и гонки, «переименована» от «родилась» не
  отличить; у git уже есть чистый курсор.
- Вебхуки/RPC-пуш — отложено: локальная система, файловый канал дешевле; пуш появится вместе
  с сетевым консьюмером.
- Чтение чужих лент/историй — отвергнуто: посылка материализуется коммитом в репо получателя, локальной ленты достаточно.
- git-HEAD тула как версия — отвергнут: шумит на не-поведенческих коммитах; content-hash/голова чейнджлога точнее.
- Регенерация чейнджлога ритуалом разработчика — отвергнута: автоген по событию (пост-коммит), дрейф невозможен по конструкции.

## Provenance

Человек (дословно): «Блин, ну получается это тоже естественная точка расширения - хуки на
события caped. Это ж одно и то же - увидеть что появилась новая идея от соседнего агента или
ремайндер в сессию отправить когда он чейндж заархивировал?»; «делать парсинг истории в плагине
- неправильно, для этого же и есть тул наш блин, просто надо как-то определиться как хуки
работать должны чтобы плагин мог на них подписываться».

Агент (внешний консьюмер, автор `caped-context`, имея в виду опыт интеграции): контракт ленты
(jsonl + курсор) — по аналогии с траекториями сессий; отделение нотификации от энфорсмента —
по модели «хук vs совесть».

## Open questions

Отвечены при финализации (гейт вопрос-лайфсайкла):

- O1: РЕШЁН — единый feed.jsonl, курсор = число прочитанных строк, `caped events --since <n>`.
- O2: РЕШЁН — события состояний проверок (trace-red/check-red) вне v0; точка расширения задепонирована в `ideas/_backlog` (запись 2026-08-23).
- O3: РЕШЁН — пишет post-commit шим (реализован); самопроверка версии тула (tool-updated/чейнджлог) — фаза 2, запись в `ideas/_backlog` (2026-08-23); мультиагентные пуши и однокомп-агенты — забота плагина/агентов, передано в multiagent-events.
- O4: РЕШЁН — ротация ленты: обрезка по N=1000 строк при запуске `caped events` (удаляются строки до последних 1000), курсор = строка-индекс, переживает обрезку.
