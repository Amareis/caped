## Why

Маркеры требований — один неймспейс на репо. Вендоренные файлы caped (проза дампа в `scripts/caped.sh`, комментарии `caped-render.py`/`caped-check.py`) цитируют ~43 маркера, чьи дефы живут в спеке репы ТУЛА. В adopting-репе (первый живой случай — секретарский dsh-плагин) trace читает их как refs без дефов → десятки dangling, сигнал тонет в шуме тула. Сейчас это закрыто site-patch'ем в репе плагина (`caped-trace.sh` исключает `scripts/*` из refs-скана) с пометкой «handoff caped#trace-ignore-tool при будущем слиянии» — локальный патч умрёт при обновлении тула и не переносится на другие adopting-репы (kudach следующий).

## Context

Ключевое наблюдение человека: скрипты резолвят рабочую репу через `git rev-parse --show-toplevel`, хуки гит запускает с cwd = корень репы — скриптам незачем лежать внутри adopting-репы вообще. Без вендоринга проблема чужих маркеров исчезает конструктивно, а не фильтруется. Это же направление уже записано в caped-cli для бинарника v0.1 («шимы на `exec caped hook ...`, шелл-скрипты удаляются») — linked-режим делает то же для шелл-версии сейчас. В репе тула ничего не меняется: она self-host'ится, её `scripts/` — её контент, цитаты дампа load-bearing для `undumped` ({#trace-dump-attr}). Попутно: второй потребитель (плагин через caped) активировал оговорку нормы {#trace-dump-attr} про генерализацию атрибутов — соседний вопрос (O3).

## Requirements

- Linked-режим установки: тул ставится один раз на машину (git checkout в известном месте, далее `~/.local/bin/caped` или PATH); `caped init` в adopting-репе НЕ требует `scripts/caped.sh` внутри неё, а ставит шим хука, указывающий на установленный диспетчер (резолв: `$CAPED_HOME`, затем PATH, затем путь, откуда запущен init). Репа держит только шим, `caped.registry`, `ideas/`, `changes/`.
- Self-host репа тула продолжает работать как сейчас (свои `scripts/` — свой контент); режим различим по факту «репа — дом тула» (init помечает linked-репу, например записью в `.git/config` или `.caped/`), trace и check в linked-репе не видят файлов тула by construction.
- AGENTS.md-стаб adopting-репы указывает на `caped` (PATH), а не на `bash scripts/caped.sh` — агент в linked-репе вызывает установленный тул.
- Обновление тула: linked-репы получают новую версию сразу (это и цель — site-patch плагина умирает сам); поведенческий риск автообновления фиксируется, не решается здесь (O2).
- Подтверждение на живом потребителе: секретарский dsh-плагин переходит с site-patch'а на linked-режим; его patch-note про `caped#trace-ignore-tool` резолвится.
- Тесты: фикстурная adopting-репа, init'ed в linked-режиме (тул лежит вне репы) — хук энфорсит, check/trace/render работают, trace зелёный без единого dangling от маркеров тула; self-host сценарии существующих suites не меняются.

## Decisions

- Направление выбрано человеком (2026-08-23): «надо просто сделать, чтобы тул мог использовать напрямую без вендоринга, это ж несложно?» — не фильтровать маркеры вендоренных файлов, а устранить вендоринг; манифестно-исключательная схема (первая редакция требований) ушла в отвергнутые.
- Резолв пути тула упрощён до «откуда запущен диспетчер» (`dirname $0` init-скрипта): `$CAPED_HOME`/PATH-резолв в шиме не нужен — шим пишется один раз с абсолютным путём, а `caped` wrapper в корне тула даёт PATH-вызов для человека и агента. Self-host различим конструктивно: диспетчер внутри ROOT → шим репо-релятивный (переживает перенос репы), снаружи → абсолютный. Записи «linked-репа» в `.git/config` не введено — режим виден из самого шима.
- AGENTS.md-стаб сидится только при отсутствии файла (у kudach и плагина он уже есть — не трогаем) и указывает на wrapper абсолютным путём; переезд на PATH-имя `caped` — косметика, которую репа сделает сама при желании.

## Rejected alternatives

- **Манифест «наших файлов» + исключение из refs-скана** (первая редакция) — машинерия (запись, хэши, обновление при апгрейде тула) под проблему, которая исчезает без вендоринга; к тому же ломается на локальных правках вендоренных скриптов.
- **Хардкод `scripts/*` в trace** — то, что сделал site-patch: в репе тула тот же путь несёт свои цитаты; путь не несёт роли.
- **Неймспейс-префиксы в маркерах** (`[#caped:render-json]`) — тяжёлая перестройка синтаксиса и всех существующих маркеров ради случая, который решается установкой.
- **Подтягивать дефы из спеки репы тула** (удалённый резолв) — adopting-репа не должна зависеть от сети/копии чужого README при проверке своих маркеров.

## Provenance

Человек (дословно, передав сообщение dsh-агента):

- «плагин — это второй потребитель, он его делает через caped же — …Один документированный site-patch: caped-trace.sh исключает scripts/* из refs-скана — проза дампа и комментарии рендера несут маркеры тула (43 штуки), которые определены в спеку репы-тула, а не нашей. Пометка в самом патче: хендофф caped#trace-ignore-tool при будущем слиянии (это ровно класс „находка адресует другой контракт“ из #territory-handoff)»
- «Надо это куда-то нам?»
- «Мне вообще кажется, что надо просто сделать, чтобы он тул мог использовать напрямую без вендоринга, это ж несложно?»

Додумано агентом (с основаниями):

- Маршрут: новая идея с именем из handoff-метки (`trace-ignore-tool`), чтобы ссылка в чужом патче резолвилась по имени — основание: {#territory-handoff} требует передачи в контракт цели; цель — наш trace/установка, живого чейнджа по ней нет.
- Техническая оценка «это несложно» подтверждена чтением кода: `scripts/caped-init.sh:25` требует вендоренный диспетчер, но `caped-render.py`/`caped-check.py`/хук резолвят ROOT через `git rev-parse` — местоположение скриптов им безразлично; шим на внешний путь — единственная правка сути.
- spawned_from: e2e-harness-realism — основание: находка порождена работой над секретарским dsh-плагином, обсуждённой там (O3); территория находки — установка/trace, не харнес.

## Open questions

- O1: где живёт «установленный тул» для шелл-версии — фиксированный путь (`~/.caped/tool`), git submodule, или сразу дождаться бинаря caped-cli; критерий: одна команда установки, восстанавливаемо на новой машине.
- O2: автообновление linked-реп на новую версию тула без consent'а репы — нужен ли пин версии (запись в реестре/конфиге репы) или раннее предупреждение «тул новее, чем репа видела»; поведенческий риск, не блокер.
- O3: второй потребитель активировал оговорку про кастомные атрибуты ({#trace-dump-attr}) — плагину нужны свои атрибуты или хватает закрытого набора; спросить при его миграции на linked-режим.
