## Why

Ручной релей идей между репами уже повторён трижды (e2e-guard-retire — к нам,
idea-edited-consumer и kimi-code-plugin — к соседу), каждый раз вручную: скопировать
файл, адаптировать фронтматер, коммит с `Idea:` в чужой репо, снять локальную копию.
Процедура не формализована: ни списка соседей, ни команды, ни вывода в туле —
прибывающий агент не знает топологию проекта.

Второй контур той же проблемы (2026-08-24): агенты начали коммитить в соседние репы
НАПРЯМУЮ (kimi-cli правил идеи в caped и caped-context вживую). Это ломает петлю
обратной связи: плагин агента сидит на фиде ДОМАШНЕЙ репы и `commit-rejected` чужой
репы не увидит никогда; хук целевой репы не знает ни кто агент, ни где его дом.
Дешевле закрыть прямые гостевые коммиты, чем учить весь контур кросс-репо
идентичности.

## Context

Живой кейс 2026-08-24: caped-context (dsh-плагин) — сосед без remote, его сессия
просыпается по idea-born своей ленты и закрыла релей idea-edited-consumer целиком
(архив ef251eb + адхоки feed-unknown-json, intent-from-events). Соседская сторона
готова; наша — процедура вручную. Мультирепа-топология принадлежит репо, а не тулу:
в bare-дамп (нейтральность, {#dump-neutrality}) список соседей не входит — это
данные репо, как `caped.registry`. Формат данных — файл в корне по образцу реестра
(TAB: имя, путь, роль), конфиг-алия вне дерева отвергается (прецедент «конфиги не
используем» — там про CLI-настройки; список соседей — данные топологии, как реестр).

Идентичность агентов (трейлер `Agent:`, presence-файлы `.caped/sessions/*.jsonl`) —
территория идеи multiagent-events; эта идея её ПОТРЕБЛЯЕТ для допчека резидентства.
Петля «отказ → наг с именем» работает только в домашней репе (плагин читает её фид) —
отсюда запрет прямых гостевых коммитов.

## Requirements

- Файл соседей (например `caped.neighbors`, TAB: name, path, role) в корне репо;
  `caped check` валидирует формат.
- `caped relay <сосед> <идея>`: копирует `ideas/<name>.md` в `<путь соседа>/ideas/`
  с адаптацией (spawned_from: null, заметка о релее из этого репо в Context/Provenance),
  коммит там `Idea: <name>` (их хук энфорсит), затем по умолчанию снимает локальную
  копию (`Archives: <name>` + причина); флаг `--keep` оставляет локальную.
  Проверка: сосед — капед-репо (.git + registry), имя свободно у соседа.
  Relay — туловая команда и сам знает home (репа вызова): штампует происхождение
  (`relayed from <home>@<hash>`) без какой-либо гостевой идентичности в трейлерах.
- Прямых гостевых коммитов нет — агент коммитит только в домашней репе, влияние на
  соседа идёт через relay. Подкрепляется допчеком commit-msg хука: сессия из
  `Agent: <harness>/<sid>` ОБЯЗАНА иметь presence-файл в `.caped/sessions/` этой репы;
  нет файла и id без суффикса `@<home>` — отказ с явным текстом («не твоя репа —
  общайся `caped relay` из домашней, или подпишись `<id>@<home>`»). Исключения:
  `Agent: human` (хозяин без сессии) и `<id>@<home>` — осознанный эскейп для
  адхок-хотфиксов, честно маркирующий чужака.
- Вывод: `caped plan` показывает соседей (имя, путь, роль) — полнота сведений о
  проекте; отдельная команда/вид не обязательна в v0.
- Релей виден в нашей ленте событий: снятие локальной копии событится как
  `idea-withdrawn` (пробел закрыт архивом idea-withdrawn-event, d735d5a).

## Decisions

- Данные соседей — файл в дереве (по образцу `caped.registry`), не `.caped/`-конфиг:
  топология — факт репо, коммитится, виден в плане; хидден-конфиг дрейфовал бы.
- `--keep` по умолчанию? Нет: «хэндофф идей» = передача владения, локальная копия
  снимается (прецедент kimi-code-plugin); `--keep` — для случая «у соседа своя идея,
  у нас своя» (idea-edited-consumer).
- Команда ходит напрямую в рабочее дерево соседа (у соседей нет remote — живой кейс),
  не через fetch/push.
- Дверь в чужую репу одна — relay (2026-08-24, человек: «не надо туда лезть напрямую,
  используй relay который уже корректно все проверит и home он знает»). Следствия:
  суффикс `@<home>` в `Agent:` не нужен для штатной работы (только эскейп-хотфикс);
  проблема «cwd промпта не доказывает дом» и «плагин не видит чужой commit-rejected»
  снимаются вместе с классом гостевых коммитов.
- Допчек резидентства — по факту presence-файла (`.caped/sessions/`), не по реестру
  агентов (человек 2026-08-24: «если сессии указанной в agent нет в репе — надо
  ошибку соответствующую писать»): реестр агентов — ещё одно дрейфующее состояние,
  presence-файл пишется плагином по факту работы.

## Rejected alternatives

- Продолжать вручную: процедура повторена трижды, каждая переносит ошибки (адаптация
  фронтматера, забытый `Archives:` на нашей стороне). Отклонено.
- Синхронизация через общий remote (fetch/push): у соседей remote нет; топология —
  локальные рабочие копии. Отклонено.
- `.caped/neighbors` (скрытый конфиг): невидим в плане без отдельного рендера, дрейф
  вне дерева. Отклонено в пользу коммитимого файла.
- Класть список соседей в bare-дамп: нарушает нейтральность дампа, данные репо не
  переносятся. Отклонено.
- Гостевые коммиты с полной кросс-репо идентичностью (`@home` обязательным, хук
  резолвит дом, плагин следит за фидами всех соседей): обсуждено 2026-08-24 и
  отклонено — контур обратной связи (наг) всё равно не замыкается за границей репы,
  а relay уже несёт home бесплатно.

## Provenance

Человек (дословно, 2026-08-24): «Еще одна идея - как нам формализовать нашу текущую
мультирепа структуру? Чтобы например хэндоф идей соседу можно было делать через cli
тоже? И чтобы это тоже в выводе тула было для полноты сведений о проекте и соседях?»;
«Не уверен, не уверен вообще, как это будет работать? Проверку делает хук - он не
знает где там дом агента, а инжектит инфу плагин который смотрит на ивенты... в родной
папке, он вообще commit rejected не увидит в той папке!»; «это в целом просто означает
что и не надо туда лезть тебе напрямую, используй relay который уже корректно все
проверит и home он знает»; «если сессии указанной в agent нет в репе - надо ошибку
соответствующую писать, чтобы общался релеем а не сам лез (ну либо указывал свой
проект в имени). Это на случай хотфиксов адхоков уже»; «надо было ее даже быстрее
делать чем мультиагентность в одной репе, это уже сейчас живой кейс по факту».

Додумано агентом (с основаниями): файл-данные по образцу реестра, а не конфиг —
основание: топология — факт репо (реестр уже так работает, neutralize); ручные релеи
— 3 прецедента (см. Why). Прямые коммиты kimi-cli в caped/caped-context 2026-08-24
(депозиты в _backlog, правки multiagent-events, идея kimi-agent-presence) — живой
антпример, который правило «только relay» закрывает.

## Open questions

- O1: строгий ли это `events`-тип «relayed» в нашей ленте или достаточно события
  снятия (idea-withdrawn уже эмитится)?
- O2: роль соседа (plugin/adopting/upstream) — обязательное поле или свободное?
- O3: неидейные правки за границей (хотфикс кода соседа): строгое правило — релеишь
  идею-заказ, резидент имплементит; `@home`-коммит — эскейп. Где граница между
  «заказом» и «хотфиксом»?
- O4: ложные отказы допчека при сессии без presence-файла (живой кейс 24.08: сессия
  kimi-cli работала на старом снапшоте хуков — ленту получала, presence-файла не
  имела; под таким чеком её коммиты были бы отклонены). Rollout: сначала warn-режим,
  enforce — когда плагины массово пишут сессионные файлы?
