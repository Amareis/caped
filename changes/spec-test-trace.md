## Зачем

Тесты зеркалят требования (правило из test-hooks), но связь сейчас держится на памяти: переформулировка или
удаление требования молча рвёт её. Нужна машинопроверяемая трассировка хотя бы на уровне имён — иначе спеки и
тесты разъедутся рано или поздно (прямая цитата).

## Контекст

Прецедент kudach: там уже выбран паттерн «зеркальные имена и ссылки из README» для e2e — эта идея его
формализует. Ранее отклонённая «генерация спек из тестов» не противоречит: направление строго спека → тесты,
никакой генерации прозы. Ключевое упрощение: трассировка — статический анализ текста, тесты запускать не
нужно, поэтому язык проекта почти неважен и система плагинов вырождается.

## Требования

1. Маркер в спеке: `[#<slug>]` инлайн в прозе буллета. ID стабилен, проза вокруг свободна.
2. Ссылка из теста тем же маркером: в имени сценария/теста или комментарием над ним.
3. Чекер `caped trace`: скан `git ls-files` (бесплатно уважает .gitignore);
   три отчёта — требование без единой ссылки, ссылка на несуществующий ID, дубликаты ID. Проверяются только
   enforced-капы.
4. Явное освобождение: `[#<slug> no-test]` для процессных/доковых требований — невидимое исключение хуже
   правила.
5. ~~Статусы тестов (JUnit XML, `test_run`/`junit`/`test_filter`)~~ — перенесено в идею `test-status-junit`
   (spawned_from: spec-test-trace) по правилу «отложенный скоуп — находка».
6. ~~materialise рендерит матрицу покрытия~~ — туда же, в `test-status-junit` (матрице нужны статусы).

## Решения

- Маркер `[#<slug>]` по дефолту (инлайн в прозе буллета, не отдельным списком — отдельный индекс требований
  был бы write-only слоем; маркер умирает вместе с предложением при правке). HTML-комментарий отклонён:
  невидим в рендере.
- Чекер — отдельная подкоманда `caped trace`, статическая (git ls-files + grep, без JUnit на v0): defs —
  маркеры в spec-файлах enforced-кап реестра, refs — маркеры во всех tracked-файлах кроме spec-файлов и
  ideas//changes/ (проза, не покрытие). Падения: uncovered / dangling / duplicate, сообщения — инструкции
  на английском. Trace — ручная/CI-проверка, не хук: до коммита новых тестов refs не видны (ls-files —
  индекс), это нормально.
- Плейсхолдер в документации — `[#<slug>]` с угловыми скобками: не матчится регэкспом маркера, иначе
  описание конвенции само становится ложным определением (поймано догфудингом на первом же прогоне).
- Ретро-маркировка (README caped + суффиксы в сценариях) — в этом же чейндже: та же территория контракта,
  иначе trace на собственном репо не сойдётся.
- JUnit/статусы и `test_run`-конфиг вырезаны в идею `test-status-junit` тем же коммитом, что и вырезание —
  первое применение правила «отложенный скоуп — находка» (зафиксировано этим чейнджем в README и дампе).
- Найдено реализацией: awk-разбор defs/refs обязан различать файлы по ARGV, а не NR==FNR (пустой файл ссылок
  ломает идиому); подшеллы в тестах не возвращают счётчики — сценарии бегут в основном шелле; фикстурные
  маркеры в тестах собираются через переменную (`${MK}alpha]`), чтобы исходник теста сам не читался как ref
  при прогоне trace на настоящем репо.

## Променанс

Человек: «как-то надо связать спеки ридми с тестами, хотя бы на уровне названия требований, иначе точно
разъедутся»; «неизвестно, какой язык на проекте и как тесты запускаются — какая-то система плагинов
понадобится, что ей надо? название и статус как минимум?».

Агент (основания): отклонены чистое зеркалирование имён (переформулировка молча рвёт связь — ровно тот дрейф,
от которого страхуемся) и индекс-без-чекера (отчёт никто не читает, пока сломано); плагины вырождены, потому
что name/discovery — это grep по маркеру, а status — JUnit-конвенция; `git ls-files` как вселенная файлов
снимает проблему «куда сканировать». Вариант C (только матрица) — не замена чекеру, а его рендер.

Человек (середина чейнджа): «junit надо видимо в отдельную идею вытащить тогда — иначе потеряется. И это
кстати тоже важный момент для воркфлоу, надо где-то зафиксировать его» → идея `test-status-junit` +
правило «отложенный скоуп — находка» в README (лайфцикл) и дампе (DISCIPLINE).
