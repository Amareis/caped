## Why

В репо уже работают несколько агентов параллельно (kimi-code CLI + dsh web, живой кейс 2026-08-23: один вёл чейндж, второй-оценщик о нём не знал). Состояние едино, потому что носитель — гит; но у прибывающего/работающего агента нет способа узнать, что изменилось, пока он работал: новые идеи, взятые в работу чейнджи, архивации, адхок-решения. Хук формат защищает, территорию — нет.

## Context

`render plan` (идея render-first) отвечает «что в работе сейчас», но не «что произошло с точки X». Лента событий — тот же derived view, что history, но инкрементальный: события из трейлеров (`Idea:` — рождение, mv-коммит с `Change:` — взятие в работу, `Archives:` — архивация, fileless contract — адхок) с датой и хэшем. Pull вместо push: сервера не надо, состояние не дрейфует; push (web-сервер, вебхуки) — поздняя фаза поверх того же view. Захват работы: `depends_on` уже гейтит; «assignee» не нужен — первый work-коммит с `Change:` и есть захват, реконструируемо из гита.

К 2026-08-24 транспорт существует: шим эмитит события в `.caped/events/feed.jsonl` (включая
`idea-edited` и `idea-withdrawn` — последний заархивирован d735d5a), плагин kimi-caped
доставляет ленту на UserPromptSubmit и пишет `.caped/sessions/*.jsonl` (заголовок:
session/cwd/root/gitBase; записи ходов с `t`; маркер конца `{"type":"end"}`). Хук-состав
kimi зафиксирован в kimi-hooks-v2 (репа caped-context): UserPromptSubmit — инъекция,
PreToolUse — блокируемый mid-step, SessionHeartbeat — observation-only (файлы писать можно,
контекст инъецировать нельзя), SessionEnd — факт exit/archive.

## Requirements

- `caped render events [--since <commit|date>]` — хронологическая лента событий трекера из трейлеров git log: рождение идеи, взятие в работу, архивация, адхок contract-коммиты. Без `--since` — за разумное окно (например, последние 50 событий).
- Агент дёргает ленту в начале сессии (после дампа и плана) и по необходимости в длинных сессиях; точка отсечения — момент начала сессии, курсор хранится у агента, не в репо.
- Тесты: сценарии в `tests/render/test_render.sh` по образцу history (фикстурные коммиты с трейлерами, ассерты по выводу, граница --since).
- Идентичность агента в коммите: трейлер `Agent: <id>` на ВСЕХ коммитах (ручные коммиты хозяина — `Agent: human`; человек подтвердил 2026-08-24: «вручную я не коммичу практически»). Хук отклоняет коммит без `Agent:` — отказ это событие `commit-rejected` (уже эмитится), плагин на нём напоминает агенту его id. Подписи harness-уровня: `kimi-cli`, `dsh`; коллизию сессий одного харнесса разрешает суффикс (`kimi-cli/486d59`); хост (`@macpro`) — только с мультимашинностью. Лента и `render history` показывают агента; легаси-коммиты без трейлера рендерятся как `unknown`.
- Подпись — факт транспорта, не самодекларация: идентичность агенту СООБЩАЕТ плагин (строка `you are <id>` в инъецируемом контексте, тот же канал, что лента и live-state); агент никогда не вычисляет свой id из путей/процессов (утечки форматов — не контракт). Плагин в git-хуки не лазит: хук принадлежит тулу, плагин — харнессу.
- Presence-вью: `caped render agents` — derived view над `.caped/sessions/*.jsonl`: строка `agent/shortid | жив (бит N мин назад) | с HH:MM | «первый промпт, усечённо»`; живость = нет end-маркера + mtime свежее порога (~10 мин, подобрать) на момент ЧТЕНИЯ; завершённые — по end-маркеру, крашнувшиеся — «пропал (нет end, молчит N)». Хранимого presence-статуса нет: mtime и есть состояние; heartbeat — плагин тачит файл раз в 2–3 минуты (activity-хуки + SessionHeartbeat для idle), отдельных beacon-записей не делаем, пока mtime не солжёт. Машино-локально: v0 видит только сессии этого хоста; мультимашинность — фаза пуша.
- ~~Пробел снятия идей~~ — ЗАКРЫТ (архив idea-withdrawn-event, d735d5a): `D ideas/*.md` + `Archives:` эмитит `idea-withdrawn` в фид.
- Правки идей видны — закрыто транспортом: шим эмитит `idea-edited` (наблюдено в ленте плагина 2026-08-24).

## Decisions

- Петля идентичности (2026-08-24, с человеком): плагин инъецирует `you are <id>` → агент пишет `Agent:` → хук требует → на отказе наг плагина напоминает имя. Каждый делает своё: тул — принуждение (хук его), плагин — знание (харнесс его), агент — дисциплина (контекст его).
- Скоуп обязательности `Agent:` — все коммиты, ручные — `Agent: human` (человек: «вручную я не коммичу практически»).
- Рендер сессии: `agent/shortid` + время старта + усечённый первый промпт как подсказка «что делает»; без поля `agent` в заголовке — голый shortid (сигнал обновить плагин). Отдельных имён сессий и генераторов имён не вводим.
- Каденция опроса ленты (было O2): старт сессии + доставка плагином (mid-step PreToolUse, накопленный хвост после простоя); таймерного опроса из агента не надо.
- Подсказка хука «N новых событий» (было O3): нет — хук безсостояниевый, точку отсечения взять неоткуда; доставка — территория плагина.

## Rejected alternatives

- **Push-уведомления (сервер/вебхуки)** — поздняя фаза; потребитель v0 — агент с CLI, pull покрывает его без инфраструктуры. Тот же event-view позже отдастся и в веб.
- **Поле assignee во фронтматере** — статус-флаг, который надо не забыть переключить: гарантированный дрейф (та же граница, что у отклонённых статус-флагов); захват выводится из первого work-коммита.
- **Курсор «since» в репо** (файл/.caped/) — чужое состояние в общем дереве; курсор принадлежит агенту и живёт у него.
- **In-file heartbeat-записи** (`{"type":"heartbeat"}`) — версия формата и мусор в jsonl ради того, что mtime уже даёт; апгрейд, только если mtime доказуемо солжёт (копирование/синк каталога).
- **Штамп трейлера из prepare-commit-msg плагином** — плагин в git-хуки не лезет (хук — территория тула); молчаливая правка сообщений за спиной агента ломает «агент пишет осознанно».
- **Самоопределение агента по путям тулов/процессам** — утечка формата, а не контракт; id сообщается плагином.
- **Человеко-читаемые имена сессий** (`brave-fox-42`) — маскировка отсутствия имени; shortid честнее и grep-абельнее по файлам.

## Provenance

Человек (дословно):

- «интересно, так-то для мультиагентной работы caped как можно адаптировать? Один сценарий уже вижу — чтобы все агенты получали оповещения в процессе работы о новых/взятых/выполненных идеях/чейнджах»
- (2026-08-24) «в туле в дискавери же должно прилетать что есть соседние агенты прям щас в сессии? поддержка тула должна быть не только в рамках трейла агента»
- (2026-08-24) «хартбит плагин и так может писать, типа там каждые несколько минут дополнять (или просто тачить) файл если идет работа же? mtime конечно такое себе, с другой стороны тогда не надо какие-то отдельные биконы делать»
- (2026-08-24) «плагин не лазит в prepare commit, это делает тул… плагин должен просто инжектить тебе имя/айди в контекст… в туле делаем agent обязательный и на конкретно ошибку отсутствия айди агента сразу еще и напоминаем ему его имя»
- (2026-08-24) «вручную я не коммичу практически. Плюс надо предусмотреть в истории еще рендеринг агентов»

Додумано агентом (с основаниями):

- Pull-лента как derived view, а не push — основание: носитель уже гит, лента реконструируется из трейлеров без новых сущностей; push требует сервера и добавляет состояние, которое может дрейфовать (контраст с постулатом «состояние выводится, не хранится»).
- Захват = первый work-коммит с `Change:` — основание: событие уже фиксируется трейлером; отдельный механизм локов дублирует то, что гит уже записал.
- Маршрутизация: новая идея (не расширение render-first) — основание: другая территория решений (инкрементальная лента vs разовый осмотр состояния), хотя контекст общий.
- Трейлер `Agent:`, а не git-author или поле в файлах — основание: git-author у всех агентов одинаковый (коммитит хозяин репо, подтверждено `git log --format=%an` 2026-08-23); поле в файле дрейфовало бы, трейлер — факт коммита, лежит в той же механике, что `Idea:`/`Change:`. Человек прямо попросил донести: «про идентичность докинь».
- Пороги presence (бит 2–3 мин, смерть ~10 мин) — основание: три пропущенных бита до «мёртв» убирают ложные смерти в длинных ходах, краш детектится за минуты; метрика некритичная, точность не нужна.

Живой кейс 2026-08-24 (kudach, два агента в одной репе — kimi-cli и dsh-харнесс): kimi-cli создал тест-идею `plugin-smoke-test` с инструкцией «снять после проверки» без исполнителя → событие `idea-born` увидели ОБА агента, dsh снял идею первым (6202428), kimi-cli пошёл снимать её же и уткнулся в уже сделанное; параллельно человек не понял, кто удалил строки из бэклога («я ничего не делал, куда пропало» — git-author общий). Три класса отказов разом: thundering herd на одно событие (F1), невидимое авторство (F2 — второй живой аргумент за `Agent:`), молчаливое снятие идеи (F3 — закрыто d735d5a). Гит-состояние и хук выдержали: потерь не было, только гонка и растерянность человека.

- Находка потребления фида (сессия не будится на события чужих коммитов: idea-edited 7585f68/eab68bb в фиде, инжекта в сессию не было) — handed off → plugin-wake-gap в caped-context (релей 2026-08-24, 27201f8); пересекается с wake-лимитами kimi-hooks-v2.
