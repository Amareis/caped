## Why

Потребитель view'шек — агент (README: «CLI первым, его потребитель — агенты»), но вывод — fixed-width таблицы для глаз: агент читает их «на глаз» и ошибается на ровном месте (живой кейс: оценщик не понял из плана, что complete-rules-dump уже ведётся). Формат не раскрывает того, что модель обещает: «план — граф, а не дрейфующая проза» (нет ни блокировок, ни графа), «одна сущность, три состояния» (history не отличает идею от чейнджа — «(in work or idea)», хотя статус читается из местоположения файла).

## Context

Текущий вывод (scripts/caped-render.py): plan — `name last: дата хэш (Nd ago) [STALLED]` без сабджекта последнего коммита; ideas — `name phase priority deps: [py-list] from: null` (утечки реализации); сортировка по priority, phase вперемешку; history собран из трейлеров, для неархивированных — «(in work or idea)»; coverage — только агрегаты по состояниям. README обещает граф по phase/priority/depends_on и гейт «нельзя в работу, пока зависимость не архивирована» — в выводе заблокированные идеи не помечены. Параллельная идея multiagent-events планирует `render events --since` — общий JSON-слой с plan нужен, чтобы не дублировать генератор.

## Requirements

1. JSON-режим: `caped render <view> --json` — стабильные ключи (name, status, phase, priority, deps[], spawned_from, last_commit{date,hash,subject}, age_days, stalled, blocked); text остаётся дефолтом; --write не трогаем.
2. План, `last:`: добавить сабджект последнего коммита (`git log -1 --format=%s` — вызов уже есть) — `last: 2026-08-23 e109fed «в работу» (0d ago)`.
3. План: маркер `BLOCKED (dep unarchived)` для идей, чьи depends_on не заархивированы (архив — из `Archives:`-трейлеров, тот же код, что в caped-check); группировка/сортировка по phase, затем priority.
4. История: живой статус неархивированных сущностей из файловой системы (`ideas/<name>.md` → idea, `changes/<name>.md` → in work) вместо «(in work or idea)» — дополнение человека: «никто же не мешает быстро файлы чекнуть сразу».
5. Coverage: per-cap строки (сколько файлов под каждой капой) + топ свободных путей — в text и JSON.
6. Полировка строк: deps без Python list repr (`deps: a, b`), `from: —` вместо `null`, возраст относительным или только при застое.
7. Тесты: сценарии `tests/render/test_render.sh` обновлены под новый формат; `caped.sh trace` и `just test` зелёные.

## Provenance

Человек (дословно):

- «По формату вывода рендера есть идеи?»
- «Запиши, еще кстати лично мое дополнение: session-export  2026-08-22 bdf19e09 - (in work or idea) — Вот это "или" странная фигня - так-то никто же не мешает быстро файлы чекнуть сразу чтобы понять где и что оно сейчас»

Додумано агентом (с основаниями):

- JSON-режим опт-ином, text дефолтом — основание: README «CLI первым, потребитель — агенты», но человек всё равно смотрит глазами; `--json` ничего не ломает (stdout-only, read-only).
- Живой статус в history из каталогов — основание: «статус не хранится — выводится: файл в ideas/ = идея, в changes/ = в работе» (README); листинг двух каталогов — тот же код, что в entities(); «(in work or idea)» — ложная двусмысленность, снимаемая тривиально.
- blocked по depends_on vs Archives-трейлерам — основание: README «depends_on — гейт: нельзя в работу, пока зависимость не архивирована»; источники архива — трейлеры (как в caped-check known_entities), без новых статусов.
- Сабджект в last: — основание: хэш+дата без сабджекта не отвечают на «что с чейнджем произошло»; это же сняло бы живой кейс оценщика («почему in work?»).
- Связь с multiagent-events: один генератор данных (фронтматер+трейлеры) для plan/events — основание: не дублировать формирование общих полей, JSON-схема одна.

## Open questions

- O1: форма JSON — плоские ключи vs вложенный объект; согласовать с `render events --json` (multiagent-events) до реализации, чтобы схема была одна.
- O2: `--json` только для machine-потребителя или и `--write` с JSON-файлами? Рекомендация: `--write` остаётся markdown-материализацией для глаз, JSON — stdout-only.
- O3: семантика blocked — только depends_on-гейт (README) или также stalled? Рекомендация: только depends_on; stalled — отдельный флаг.
- O4: поведение для состояний-расхождений в history (рождён по Idea:, файла нет, Archives: нет — теоретически невозможен при живом хуке): маркер «?» наружу (дрейф виден) или молчаливо пропускать? Рекомендация: «?» — drift-review смотрит историю.
