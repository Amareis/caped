## Why

Сегодня подключение caped к НОВОМУ проекту — ручная прелюдия: mkdir, git init,
рисунок README (без `## Requirements` root-кап enforced сразу красный), и только
потом `caped init`. Бутстрап одной командой закрывает путь «ноль → репа под
дисциплиной»: каталог, git, README-скелет, шимы, реестр, ideas/ с _backlog,
AGENTS.md.

## Context

`caped init` требует существующий git-репо (`die "not a git repository"`).
Реестр-скелет делает root-кап enforced → README.md, поэтому бутстрап обязан
посеять README с секцией `## Requirements` — иначе первый же check красный.
Диспетчер сейчас роняет аргументы init (`exec caped-init.sh` без "$@").

## Requirements

- `caped init <name>`: создаёт каталог (существующий НЕпустой — отказ с явным
  текстом), `git init` внутри, сидит README.md-скелет (заголовок + пустая
  `## Requirements`), затем прогоняет стандартный init в новом корне.
- Сразу после бутстрапа `caped check` зелёный (README удовлетворяет enforced
  root-капу, `_backlog` на месте).
- `caped init` без аргументов — прежнее поведение, без изменений.
- Дельта в дампе/спеке + тест: бутстрап в mktemp даёт готовую репу, повторный
  вызов на тот же каталог — отказ.

## Decisions

- Режим по АРГУМЕНТУ init, не отдельная команда: одна дверь подключения,
  «с аргументом — с нуля, без — в текущей репе».
- README-скелет минимален: `# <name>` + `## Requirements` с «-» — контент
  проекта не выдумываем, лишь валидная форма.
- Отказ на существующем непустом каталоге (а не «вливание»): бутстрап — про
  чистый старт, подключение существующего — прежний безаргументный режим.

## Rejected alternatives

- Отдельная команда `caped new <name>`: вторая точка входа для той же
  инициализации, расходящиеся пути «с нуля»/«в существующую». Отклонено —
  режим init по аргументу.
- Сидить первый коммит в бутстрапе: чужая история — решение автора проекта
  (хук без трейлеров всё равно не пустит, а --no-verify навязывать не надо).
  Отклонено.
