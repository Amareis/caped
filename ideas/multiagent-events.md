## Why

В репо уже работают несколько агентов параллельно (kimi-code CLI + dsh web, живой кейс 2026-08-23: один вёл чейндж, второй-оценщик о нём не знал). Состояние едино, потому что носитель — гит; но у прибывающего/работающего агента нет способа узнать, что изменилось, пока он работал: новые идеи, взятые в работу чейнджи, архивации, адхок-решения. Хук формат защищает, территорию — нет.

## Context

`render plan` (идея render-first) отвечает «что в работе сейчас», но не «что произошло с точки X». Лента событий — тот же derived view, что history, но инкрементальный: события из трейлеров (`Idea:` — рождение, mv-коммит с `Change:` — взятие в работу, `Archives:` — архивация, fileless contract — адхок) с датой и хэшем. Pull вместо push: сервера не надо, состояние не дрейфует; push (web-сервер, вебхуки) — поздняя фаза поверх того же view. Захват работы: `depends_on` уже гейтит; «assignee» не нужен — первый work-коммит с `Change:` и есть захват, реконструируемо из гита.

## Requirements

- `caped render events [--since <commit|date>]` — хронологическая лента событий трекера из трейлеров git log: рождение идеи, взятие в работу, архивация, адхок contract-коммиты. Без `--since` — за разумное окно (например, последние 50 событий).
- Агент дёргает ленту в начале сессии (после дампа и плана) и по необходимости в длинных сессиях; точка отсечения — момент начала сессии, курсор хранится у агента, не в репо.
- Тесты: сценарии в `tests/render/test_render.sh` по образцу history (фикстурные коммиты с трейлерами, ассерты по выводу, граница --since).
- Идентичность агента в коммите: трейлер `Agent: <id>` (например `kimi-cli`, `deepseek-web`) на коммитах агента — git-author у всех агентов один (хозяин репо), и без трейлера «кто сделал» из истории не восстанавливается (живой кейс 2026-08-23: траекторию дипсика в логе отличали от kimi только по памяти). Лента событий показывает автора-агента.
- Однокомп-агенты в одной репе (решение 2026-08-23): координация/избежание конфликтов и общение между агентами — ЗАБОТА ПЛАГИНА и агентских сессий, не тула; тул отдаёт факты (лента caped-event-hooks), а «кто что взял» реконструируется из гита. Инбокс-посылок между агентами (идея-файл как заказ + курсор ленты) — будущее расширение, связано с мультиагентным пушем: если двое крутятся в одной репе, им придётся общаться, чтобы не конфликтовать.
- Пробел снятия идей (хэндофф из neighbor-relay, 2026-08-24): `D ideas/*.md` + `Archives:` событие в фиде НЕ эмитится (ветка archived ловит только `D changes/`; живой кейс — снятие kimi-code-plugin прошло молча). Лента обязана показывать снятие/передачу — событие `idea-withdrawn` в шиме (или фиксация в derived-view `render events`), иначе релей соседу невидим в нашей ленте.

## Rejected alternatives

- **Push-уведомления (сервер/вебхуки)** — поздняя фаза; потребитель v0 — агент с CLI, pull покрывает его без инфраструктуры. Тот же event-view позже отдастся и в веб.
- **Поле assignee во фронтматере** — статус-флаг, который надо не забыть переключить: гарантированный дрейф (та же граница, что у отклонённых статус-флагов); захват выводится из первого work-коммита.
- **Курсор «since» в репо** (файл/.caped/) — чужое состояние в общем дереве; курсор принадлежит агенту и живёт у него.

## Provenance

Человек (дословно):

- «интересно, так-то для мультиагентной работы caped как можно адаптировать? Один сценарий уже вижу — чтобы все агенты получали оповещения в процессе работы о новых/взятых/выполненных идеях/чейнджах»

Додумано агентом (с основаниями):

- Pull-лента как derived view, а не push — основание: носитель уже гит, лента реконструируется из трейлеров без новых сущностей; push требует сервера и добавляет состояние, которое может дрейфовать (контраст с постулатом «состояние выводится, не хранится»).
- Захват = первый work-коммит с `Change:` — основание: событие уже фиксируется трейлером; отдельный механизм локов дублирует то, что гит уже записал.
- Маршрутизация: новая идея (не расширение render-first) — основание: другая территория решений (инкрементальная лента vs разовый осмотр состояния), хотя контекст общий.
- Трейлер `Agent:`, а не git-author или поле в файлах — основание: git-author у всех агентов одинаковый (коммитит хозяин репо, подтверждено `git log --format=%an` 2026-08-23); поле в файле дрейфовало бы, трейлер — факт коммита, лежит в той же механике, что `Idea:`/`Change:`. Человек прямо попросил донести: «про идентичность докинь».
- Этикет реакции — кандидат-правило «свои дети» (см. O7) — в скилле/инструкциях агентов, не в туле — основание: граница уже принята выше (тул отдаёт факты, координация — плагин и сессии); гит сериализует коммиты, окно гонки мало, а назначение исполнителя текстом в файле идеи («снимет автор») не требует машинерии. Живой кейс 2026-08-24 внизу.

Живой кейс 2026-08-24 (kudach, два агента в одной репе — kimi-cli и dsh-харнесс): kimi-cli создал тест-идею `plugin-smoke-test` с инструкцией «снять после проверки» без исполнителя → событие `idea-born` увидели ОБА агента, dsh снял идею первым (6202428), kimi-cli пошёл снимать её же и уткнулся в уже сделанное; параллельно человек не понял, кто удалил строки из бэклога («я ничего не делал, куда пропало» — git-author общий). Три класса отказов разом: thundering herd на одно событие (F1), невидимое авторство (F2 — второй живой аргумент за `Agent:`), молчаливое снятие идеи (F3 — уже в требованиях выше). Гит-состояние и хук выдержали: потерь не было, только гонка и растерянность человека.

## Open questions

- O6 (будущее): инбокс-посылок между агентами одной репы (идея-файл = заказ, курсор ленты = нотификация) — фаза после ленты; форма — эскиз при мультиагентном пуше (агенты в одной репе обязаны общаться, чтобы не конфликтовать).
- O7: этикет реакции на события ленты (живой кейс F1 выше): кандидат — «follow-up принадлежит агенту, чей коммит породил событие, если файл/человек не назначили иного; исполнитель может быть назван текстом в самой идее». Где живёт: текст скилла/AGENTS.md. Достаточно ли его, или нужен машинный клейм на идею (коммит «беру»), и не породит ли этикет молчание наоборот (событие, на которое не отреагировал никто, потому что «породивший» оффлайн)?
- O1: формат строки события и нужна ли фильтрация по типам (только архивации, только рождения) — с `Agent:` добавляется фильтр по автору («мои события vs чужие»), см. этикет O7.
- O2: каденция опроса — только старт сессии или и по таймеру в длинных сессиях; не превратится ли в шум.
- O3: стоит ли хуку при коммите подсказывать «с момента X появилось N событий» — хук безсостояниевый, точку X взять неоткуда; скорее нет, но обсудить.
- O4: откуда хук/агент берёт свой `<id>` для `Agent:` — env (`CAPED_AGENT`), git config (`caped.agent`), параметр сессии? И энфорсить ли трейлер хуком (на каких коммитах: всех? только tracker-событиях?) или оставить конвенцией, которую проверяет drift review.
- O5: видеть ли в ленте правки идей (M ideas/*.md): сейчас они без трейлеров by design (идеи — свободная зона), в ленту не попадут; если нужны — либо трейлер на правках, либо лента читает diff.

Связка 2026-08-23: транспорт ленты — капед-события (caped-event-hooks, feed jsonl + курсор + `.caped/hooks` дистрибуция); эта идея — потребитель (агент дёргает ленту), у них не дублируем.
