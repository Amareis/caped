## Why

Маркеры требований — один неймспейс на репо. Вендоренные файлы caped (проза дампа в `scripts/caped.sh`, комментарии `caped-render.py`/`caped-check.py`) цитируют ~43 маркера, чьи дефы живут в спеке репы ТУЛА. В adopting-репе (первый живой случай — секретарский dsh-плагин) trace читает их как refs без дефов → десятки dangling, сигнал тонет в шуме тула. Сейчас это закрыто site-patch'ем в репе плагина (`caped-trace.sh` исключает `scripts/*` из refs-скана) с пометкой «handoff caped#trace-ignore-tool при будущем слиянии» — локальный патч умрёт при обновлении тула и не переносится на другие adopting-репы (kudach следующий).

## Context

В репе тула исключение `scripts/` из refs-скана невозможно: цитаты дампа — load-bearing, их читает `undumped`-чек ({#trace-dump-attr}), и они же сейчас засчитываются как обычное покрытие (ref) для dump-атрибутных дефов. Значит, нужна форма, где поведение различается по роли файла, а не по пути: «файл тула» в adopting-репе — чужой неймспейс, в репе тула — свой. Реестр уже знает проекту «свои» пути; init знает, куда ставит скрипты тула. Попутно: появление второго потребителя (плагин через caped) активировало оговорку нормы {#trace-dump-attr} про генерализацию атрибутов — соседний, но отдельный вопрос.

## Requirements

- Trace исключает вендоренные файлы тула из refs-скана в adopting-репах: источник истины о «наших» файлах — запись, оставляемая `caped init` (например, секция в реестре или `.caped-tool` манифест с путями/хэшами), а не хардкод `scripts/*` (в тула репе пути те же, а семантика иная).
- В репе тула поведение не меняется: цитаты дампа продолжают работать и для `undumped`, и как покрытие dump-дефов; регрессия ловится существующими сценариями `tests/trace/`.
- Подтверждение на живом потребителе: секретарский dsh-плагин переходит с site-patch'а на выпущенный механизм; его patch-note про `caped#trace-ignore-tool` резолвится.
- Тесты: фикстурная adopting-репа (вендоренные скрипты с чужими маркерами + манифест) → trace зелёный; фикстура без манифеста (старое поведение) → dangling видны, то есть механизм не прячет чужие маркеры молча вне объявленных путей.

## Rejected alternatives

- **Хардкод `scripts/*` в trace** — то, что сделал site-patch: в репе тула тот же путь несёт свои цитаты; путь не несёт роли.
- **Неймспейс-префиксы в маркерах** (`[#caped:render-json]`) — тяжёлая перестройка синтаксиса и всех существующих маркеров ради случая, который решается списком файлов.
- **Подтягивать дефы из спеки репы тула** (удалённый резолв) — adopting-репа не должна зависеть от сети/копии чужого README при проверке своих маркеров.

## Provenance

Человек (дословно, передав сообщение dsh-агента):

- «плагин — это второй потребитель, он его делает через caped же — …Один документированный site-patch: caped-trace.sh исключает scripts/* из refs-скана — проза дампа и комментарии рендера несут маркеры тула (43 штуки), которые определены в спеку репы-тула, а не нашей. Пометка в самом патче: хендофф caped#trace-ignore-tool при будущем слиянии (это ровно класс „находка адресует другой контракт“ из #territory-handoff)»
- «Надо это куда-то нам?»

Додумано агентом (с основаниями):

- Маршрут: новая идея с именем из handoff-метки (`trace-ignore-tool`), чтобы ссылка в чужом патче резолвилась по имени — основание: {#territory-handoff} требует передачи в контракт цели; цель — наш trace, живого чейнджа по нему нет, вопрос больше двух коммитов (init-манифест + trace + тесты + миграция плагина).
- Манифест от init вместо детекта «похоже на файл тула» — основание: init — единственная точка, которая знает, что именно она поставила; детект по содержимому — эвристика, которая сломается на локальных правках вендоренных скриптов.
- spawned_from: e2e-harness-realism — основание: находка порождена работой над секретарским dsh-плагином, обсуждённой там (O3); территория находки — trace, не харнес.

## Open questions

- O1: форма записи «наших файлов» — отдельный манифест vs поле в реестре vs список в `caped.sh` самого тула (self-description, который init копирует); критерий: переживает обновление тула без ручной правки.
- O2: что делать с маркерами тула в ИСХОДНИКАХ adopting-репы (не вендоренных), если они процитированы в её доках — сейчас это тоже dangling; оставить как есть (редкий случай, честный сигнал) или дать механизм внешних дефов.
- O3: второй потребитель активировал оговорку про кастомные атрибуты ({#trace-dump-attr}) — плагину нужны свои атрибуты или ему хватает закрытого набора; спросить при миграции плагина на механизм.
