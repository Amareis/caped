# caped — доки и трекер, принадлежащие капабилити

## Зачем

Убрать пост-фактум ритуал синка `openspec/specs` и заодно ручные index/plan/archive. Модель: **одна сущность,
три состояния** — идея (`ideas/<name>.md`), чейндж (`changes/<name>.md`), архив (файл удалён Archives-коммитом;
состояние выводится из гита, не хранится). Каждая капабилити — кодовая, техническая или бизнесовая — имеет живой
README рядом со своими файлами. Свежесть обеспечивают машинерия, а не дисциплина: класс изменения в каждом
коммите (трейлеры, проверяемые хуком) и производные view (индекс идей, план, архив, история фичи, индекс
тестов), которые генерятся тулом, а не ведутся руками. Кураторское (ратионале, приоритеты, решения) пишется в
файлах; решения человека отделены от додумок агента — с основаниями, чтобы додумки можно было перепроверять и
не ходить по кругу второй раз.

Имя: **caped** («capability-ed»; коллизии проверены: capstan — AI-гавернанс, codicil — npm memory-ledger,
capstone — дизассемблер; у caped тёзка только из биомеда). Этот файл — корневой README тула и его учредительный
документ, по собственной модели: проект как корневая капабилити.

## Requirements

### Одна сущность, три состояния

Идея и чейндж — один файл одного формата: YAML-фронтматер (`name`, `summary`, `phase`, `priority`,
`depends_on`, `spawned_from`) + проза + променанс. Статус не хранится — выводится: файл в `ideas/` = идея, в
`changes/` = в работе, удалён из `changes/` = архив (дата = дата Archives-коммита). Папок под сущность нет.

- [#change-scratch no-test dump] Скрэтч-материалы большого чейнджа кладутся рядом с файлами и умирают при
  удалении чейнджа; параллельные чейнджи на одной ветке различаются трейлером `Change:`.

### Формат идеи/чейнджа

Набор секций у идеи и чейнджа один (у свежей идеи «Decisions» и обычно «Rejected alternatives» честно пустые): Why / Context / Requirements /
Decisions / Rejected alternatives / Provenance / Open questions. «Rejected alternatives» — отвергнутые
альтернативы с основаниями: без них по кругу ходят дважды (решение из диалога, раньше жило только в
променансе). Унификация делает mv в работу по-настоящему чистым — никакого
переходного коммита «реструктуризации». У чейнджа внизу опционально добавляются секции — типично **Tasks**
(туду-лист этапов большой задачи). `caped check` валидирует фронтматер и наличие базовых секций (входит в
verify) — это замена openspec-валидации SHALL-грамматики: проверяем структуру, не формальность.

- [#question-promotion no-test dump] Промоушн вопросов: мелкий открытый вопрос отвечается прямо в чейндже и
  умирает с ним; вопрос, ставший работой, промоутится в идею (`spawned_from` фиксирует происхождение);
  отложенное «на будущее» — депозитом в `ideas/_backlog.md` (иначе гейт архивации, см. `#question-gate`).

### Реестр капабилити (адресуемость)

Машиночитаемый реестр: имя → глобы путей → spec-файл → состояние `legacy | declared | enforced`. Корень дерева —
проект как одна большая фича: корневой `README.md` играет роль README капабилити; README отвечает «что и
зачем», AGENTS.md — «как работать», не дублируются. Агент читает `caped.registry`
первым делом (сразу после дампа) — иначе он не знает, какие пути enforced; ленивая альтернатива — просто
коммитить, хук сам скажет. Прогон бизнес-капа: `ideas/newcomer-acquisition.md` → чейндж-исследование → дельта
корневого README + рождение капа `acquisition` (`caps/acquisition/README.md`) + спавн кодовых идей (лендинг под
туристов) → Archives-коммит, ни одной строчки кода.

- [#free-paths dump] Неперечисленные в реестре пути тул игнорирует by design — это путь переезда: капабилити
  вводится одним PR, репорт покрытия показывает остаток.
- [#longest-prefix dump] При пересекающихся префиксах — longest-prefix-wins; порядок строк в реестре не влияет.
- [#caps-territory no-test dump] Капабилити — область решений, не обязательно область кода. Технические капы
  (shared-слои `entities/`, `platform/`, `app/`) имеют свои README с техническими инвариантами (детерминизм,
  паттерны граф-рёбер) — настоящий дом того, что размазано по AGENTS.md; `Spec:` на их contract-коммитах
  обязателен. Бизнес-капы (marketing, acquisition, монетизация) — записи с глобами на свои доки
  (`caps/<cap>/README.md`: стратегия, инварианты «пользователи платят, организаторы бесплатно», break-even
  расчёты); хук работает и там: правка бизнес-спеки — `Behavior: contract` (смена стратегии → чейндж) или
  `internal` (уточнение формулировки), механический гейт «бизнес-решение проходит через человека» — тот же
  механизм, что CODEOWNERS, только бесплатно. Идеи отвечают на вопросы (глаголы), капы владеют территорией
  (существительные); идея становится капом, когда появляется стоячая область решений.

### Декларированные классы изменений

Коммит, трогающий код `enforced`-капабилити, несёт `Behavior: contract | internal | wip`; у `contract` —
дополнительно `Spec: <путь>` или правка spec-файла в том же коммите (для cross-cutting — `Spec: README.md`).
У `contract`-коммитов трейлер `Change: <name>` обязателен (контракт без чейндж-документа = необсуждённое
бизнес-правило); у `internal`/`wip` — опционален (багфикс не плодит церемонию; хотфикс контракта = чейндж-файл
+ код + дельта README одним коммитом). Хук проверяет существование `changes/<name>.md` по staged-дереву.
Сообщения хука пишутся так, чтобы агент чинил коммит сам, без человека; ошибка хука — это инструкция:
прочитай и почини коммит по ней, а не обходи. Энфорсит versioned commit-msg хук
(`core.hooksPath`). Роллаут: advisory → блокировка после калибровки; web_version — кандидат на временное
исключение до web-e2e.

### README капабилити рядом с её файлами

`src/features/<cap>/README.md` (или `caps/<cap>/README.md`): зачем, текущие инварианты, ссылки на архивные
чейнджи. `openspec/specs/`
замораживается read-only; миграция ленивая — README появляется при следующем касании. `docs/` остаётся только
для искренне cross-cutting нарративов; per-feature содержимое уходит в README капов. Дельт-файлов в чейндже
нет: дельта — это дифф README внутри contract-коммита, атомарно и ревьюабельно.

- [#cap-readme-authorship no-test dump] README капабилити пишется агентом в момент чейнджа из слов человека;
  изменение README — бизнес-изменение, аппрувится человеком по диффу, поэтому README обязан быть достаточно
  мал, чтобы дифф реально читался.

### Променанс решений

Идеи и чейнджи различают решения человека (дословные цитаты) и додумки агента (с основанием: логика / аналогия).
Додумка с записанным основанием перепроверяема: дрейф-ревью прогоняет вывод заново и помечает правила, чьё
основание перестало держаться. Гранулярность — требование, не предложение. Полный список рассмотренных
альтернатив хранится в файле идеи (см. ниже) — это страховка от повторного хождения по кругу.

### Производные view

Из фронтматера и гита тул рендерит по запросу: план (идеи по `phase`/`priority`/`depends_on` — граф, а не
дрейфующая проза; `depends_on` — гейт: нельзя в работу, пока зависимость не архивирована), историю/архив
чейнджей, покрытие реестра (v0-реализация — `scripts/caped-render.py`).
Исключение «`plan.md` генерится in-place и коммитится» отменено до появления потребителя: stdout-план закрывает
ту же задачу без закоммиченной копии. Впереди: `change show` (док из истории + все коммиты по
`Change:`-трейлеру), история фичи (`git log --follow` + фильтр по трейлерам), индекс тестов (doc-комменты +
имена; тесты остаются в `tests/` с маркерами требований, README капа ссылается на них).

- [#render-stdout dump] `caped render` — CLI чтения: печатает views (`plan`, `history`, `coverage`,
  `reqs`) в stdout и по умолчанию ничего не пишет.
- [#render-text-layout dump] Текстовые views выложены для глаз двумя слоями: имя сущности и маркеры
  состояния — своей строкой, summary — следующей, метаданные (last/deps/from) — последними и приглушёнными;
  `reqs` группируется по файлу-источнику, длинные сабджекты урезаются. ANSI только на TTY (NO_COLOR
  уважается): в пайпе вывод чистый, без escape-кодов — агент читает тот же текст без сюрпризов.
- [#render-json dump] Любой view имеет машиночитаемую форму `--json`: вложенный объект со стабильными ключами
  (name, status, phase, priority, deps[], spawned_from, last_commit{date,hash,subject}, age_days, stalled,
  blocked); text и JSON делят один генератор данных, text остаётся дефолтом.
- [#render-blocked dump] План помечает сущности с незархивированными `depends_on` маркером
  `BLOCKED (dep unarchived: …)` — гейт виден до взятия в работу; блокировка считается только по depends_on
  (архив — из `Archives:`-трейлеров), stalled — отдельный флаг, в blocked не смешивается. Живой статус
  неархивированных в history читается из файловой системы (`ideas/` = idea, `changes/` = in work),
  расхождение (рождена по `Idea:`, файла нет, `Archives:` нет) показывается как «?» — дрейф виден наружу.
- [#render-write dump] `--write` материализует views в `.caped/` (`plan.md`, `history.md`, `coverage.txt` +
  `.json`-форма рядом, gitignored — этого достаточно, `git add` без `-f` не пропустит).
- [#render-clean dump] `--clean` удаляет `.caped/`.
- [#render-history dump] История собирается из трейлеров git log (`Idea:` — рождение, `Archives:` — архивация;
  summary архивного — из версии файла перед удалением), ренеймы сущностей склеиваются rename detection-ом
  (`(was: …)`).
- [#render-history-adhoc dump] History дополнительно перечисляет fileless-адхоки — коммиты с
  `Behavior: contract` без `Change:`-трейлера (дата, хэш, сабжект): без этого адхок-решения выпадали бы из
  восстановления работы из истории гита. Под сабжектом — выдержка тела (~140 символов, первая
  содержательная строка ратионале): листинг — окно в суть без `git show`; полный док кластера —
  `caped change show <id>`.
- [#render-reqs dump] `reqs` — индекс требований одним view: slug + гист первой строки ({#req-form}) из
  `## Requirements` enforced-спек реестра и буллет-гисты (slug опционален) из идей и чейнджей. Быстрый
  контекст проекта без чтения файлов: чего тул требует от кода и какая работа стоит в трекере.
- [#render-first dump] Прибывающий агент после дампа и реестра осматривается `caped render plan` перед любыми
  действиями трекера (спавн, работа, находки, мнение): реестр отвечает «какие пути enforced», план — «что уже
  в работе, что заторможено, какие зависимости висят»; хук защищает формат, не территорию. History/coverage —
  по потребности.

Дрейф-ревью — эволюция ретро-репорта: сопоставление декларированного (`Behavior`-трейлеры) против фактического
(диффы). Существующий `openspec/changes/archive/` не трогаем: легаси-датасет для реконструкции и готовый
golden-корпус для `change show`.

### Веб-UI (поздняя фаза)

Тот же derived view, но live-рендер. caped — отдельный инструмент, не часть kudach, со своим сервером; веб-UI —
страницы плана/чейнджей/истории там, возможное место глазного аппрува README-диффов. CLI первым (его
потребитель — агенты), веб вторым.

### Фасады (пилот)

В принятых капабилити mod.rs объявляет сабмодули приватными, наружу — явные `pub use`. Задуманные поверхности
(`commands`, `workflow`, `mcp`, `telegram`) — фасад по умолчанию. Пилот на `feed`; судьба хелперов
(`categories`, `formatting` — публичная точка feed или переезд в platform/) решается по замерам пилота.

### caped init

`caped init` — шаг подключения репозитория: устанавливает/обновляет хук-шимы в `.git/hooks` (шимы переживают
`render --clean`, т.к. живут вне `.caped/`), сидит реестр (скан директорий фич → все `legacy`), добавляет
`.caped/` в `.gitignore`, создаёт `ideas/` и `changes/`, при отсутствии сидит минимальный `AGENTS.md` с указателем
на тул, печатает первый отчёт покрытия (в `.caped/coverage.txt`). Энфорсмент по умолчанию advisory; перевод в
блокирующий — отдельное осознанное действие после калибровки.

- [#linked-install dump] Подключаемая репа НЕ вендорит скрипты тула: `caped init` ставит шим с абсолютным путём
  к установленному тула (linked-режим; шим остаётся репо-релятивным только когда диспетчер запущен изнутри самой
  репы), репа держит лишь шим, реестр, `ideas/`, `changes/` и `AGENTS.md`-указатель. Обновление тула
  подхватывается сразу; повторный `caped init` чинит шим после переезда тула. Следствие: маркеры чужого
  неймспейса из прозы дампа физически не попадают в репо, и trace-проблема «не мои маркеры» исчезает
  конструктивно, без исключений в сканере.
- [#init-idempotent dump] `caped init` идемпотентен: повторный запуск после апгрейда тула обновляет шимы и
  ремонтирует недостающее, ничего не ломая.

### caped без аргументов — самодокументация

Единый источник правил версионируется с
кодом; диспетчер v0 уже имеет подкоманды `init`/`hook`/`check`/`render`, и шимы ставятся в финальной форме
`exec caped hook commit-msg` — при переходе на бинарь (v0.1) меняется только тул, не шимы и не AGENTS.md.
Имена секций идей/чейнджей («Why», «Decisions», …) — фиксированные строки формата (английские,
независимо от языка прозы спек), в дампе
приводятся как литералы в кавычках и не переводятся.

- [#rules-in-cli no-test dump] Правила работы с репо живут в самом туле, не в маркдауне: bare-вызов `caped`
  (в v0 — `scripts/caped.sh`) без аргументов печатает полные правила (лайфцикл, трейлеры, реестр, дисциплина,
  команды), а `AGENTS.md` сводится к стабу «первым делом запусти caped без аргументов».
- [#interface-language no-test dump] Интерфейсные тексты тула (rules-дамп, AGENTS.md-стаб, сообщения хука,
  вывод команд) — на английском; спеки (README капов, идеи/чейнджи) — на языке проекта.
- [#dump-abstract dump] Дамп открывается секцией ABOUT — зачем тул нужен и каково разделение труда (человек
  решает «что», агент — секретарская работа): агент в adopting-репе видит только дамп, и без абстракта правила
  висят в воздухе.
- [#dump-neutrality no-test] Дамп проект-нейтрален: в него входят только переносимое — идентичность тула
  (имя, FSD-like допущение) и рабочие правила; нарратив хост-проекта (история, ратионале, отклонённые
  альтернативы, роадмап) живёт в спеках проекта и в дамп не попадает. Проверка «в дампе чего-то не хватает»
  валидна только для рабочих правил: отсутствие нарратива — граница нейтральности, не дыра. Атрибута `dump` у
  этой нормы нет сознательно: правило о содержимом дампа не нужно агенту adopting-репы.

### Сам тул — по своей же схеме

Репо тула живёт по своей схеме с первого enforced-коммита — догфудинг как постоянный e2e; его капабилити: hook,
registry, index-gen, report, web-ui. Хук обязан быть быстрым: bash/rust-класс старта. v0 — шелл-диспетчер
`scripts/caped.sh`; v0.1 — однобинарный CLI, шимы при этом не меняются (уже в финальной форме
`exec ... caped hook commit-msg`). **Роадмап тула живёт в `ideas/`** (check, test-hooks, render, cli,
web, adoption...), индекс и план — derived views над ним; README несёт принципы, не план — иначе план становится
write-only слоем и дрейфует. Критерий границы v0 (принцип, не план): дисциплину не стыдно отдать второй репе и
весь цикл читается без археологии — по нему в v0 входят изменения самой грамматики процесса (их дороже менять
после накопления истории в adopting-репах), а view-над-готовым и мультиагентность откладываются в v0.1.

### События жизненного цикла — энфорсмент на коммитах

Вся работа обязана восстанавливаться из одной истории гита (цель «актуальная история без лазанья в тесты»).
Каждое семантическое событие — отдельный коммит с машиночитаемым маркером; хук растёт от проверки класса
изменения (`Behavior:`) к проверке событий:

- [#seed-commit] Бутстрап: семенной коммит с фиксированным `Change: init` — дно истории и точка отсчёта
  хуков; `Change: init` — единственное исключение, позволяющее добавить `changes/X.md` напрямую.
- [#idea-birth dump] Рождение идеи: коммит, добавляющий `ideas/<name>.md`, несёт `Idea: <name>`. Порождённая в
  работе идея — ещё `Change: <parent>` (он и так обязателен: это коммит патчсета чейнджа) +
  `spawned_from: <parent>` во фронтматере как durable-связь, переживающая сквош.
- [#take-into-work dump] Взятие в работу: чистый `git mv ideas/X.md changes/X.md` (+ фронтматер) отдельным
  коммитом с `Change: X` — без контентных правок, чтобы rename detection сшивал до/после в одну историю файла
  (`git log --follow`); mv обязан сохранять имя файла. Чейндж рождается только так — прямое добавление
  `changes/X.md` отклоняется.
- [#work-trailer dump] Работа: каждый коммит, трогающий `changes/X.md` или ссылающийся на чейндж, несёт
  `Change: X`, совпадающий с именем файла чейнджа; `Change:` обязан ссылаться на существующий файл чейнджа
  (кроме `Change: init` и архивного коммита).
- [#archival dump] Архивация: финальный коммит чейнджа применяет дельты к README капов, удаляет `changes/X.md` и
  несёт `Change: X` + `Archives: X`; удаление без `Archives:` и `Archives:` без удаления отклоняются. Финиш
  может быть одним коммитом (дельты + удаление вместе); раздельный финиш валиден, но не обязателен. Чейндж,
  меняющий поведение кода, оставляет свои сценарии в тестах — требования обретают машинопроверяемую половину
  (для самого тула: правило хука без сценария в `tests/hooks/` — процессное нарушение; для adopting-проектов:
  e2e, зеркалящие требования). Чейнджи без кодового поведения (доки, процесс) освобождены — их контракт
  проверяют хук и `caped check`.
- [#question-gate dump] Гейт архивации: отложенные («v0.1»/«позже»/«отложено») открытые вопросы чейнджа
  обязаны быть отвечены, промоутированы («промоут → X» в променансе) или осесть депозитом в
  `ideas/_backlog.md` (строка с именем чейнджа в том же коммите) — иначе хук отклоняет архивацию;
  команда-удобство `caped archive` — фаза 2.
- [#event-feed dump] Событийная лента: тул пишет факты жизненного цикла (idea born / taken into work /
  archived / adhoc / contract) в `.caped/events/feed.jsonl` (append-only, одна строка = один write(2)),
  `caped events --since <n>` читает по курсору; реакции — версионированные `.caped/hooks/<event>`
  (политика репо, как git hooks; запуск с env CAPED_EVENT/CAPED_ENTITY/CAPED_COMMIT). Нотификация ≠
  энфорсмент: события — факты ПОСЛЕ (post-commit), хук-гейты — ДО.
- [#tool-version dump] Версия тула = голова встроенного чейнджлога (view `render changelog`,
  первая строка «caped changelog: N contract change(s) · head <hash> · <дата>»): сверка с
  `.caped/state/tool-version` на запуске, смена → событие `tool-updated` в ленту; бандл
  регенерится автогеном по событию `contract`/`archived` (`.caped/hooks` в tool-репо);
  бинарь вшивает при сборке. Команда `caped version` печатает версию-строку / `--path` —
  контрактная точка для консьюмера (плагин не знает путь к бандлу сам); `--changelog` печатает
  содержимое бандла — чейнджлог ТУЛА (в отличие от `render changelog`, который рендерит контракты
  текущего репо).
- [#change-show dump] `caped change show <name>` — сущность одной командой: живой текст (FS) или финальный
  документ (из родителя Archives-коммита); таймлайн событий (рождение/взятие/архив) и все коммиты с
  трейлером `Idea:`/`Change:`/`Archives:`/`Adhoc:`; адхок-кластер собирает виртуальный документ из тел;
  неизвестное имя — ошибка exit 2 с ближайшими кандидатами.
- [#lifecycle-cmds dump] Обёртки лайфцикла: `caped idea <name> [summary]` (скелет идеи + `Idea:`),
  `caped work <name>` (чистый mv в changes + `Change:`), `caped archive <name>` — автодепозит отложенных
  OQ в `ideas/_backlog.md`, собственный гейт (полный прогон; красный = отказ архива), `git rm` + `Change:`/`Archives:`.
- [#registry-mutation no-test dump] Мутации реестра: рождение/сплит/мерж капов — contract-коммит, трогающий
  `caped.registry`.
- [#behavior-trailer dump] Класс изменения: коммит, трогающий enforced-капу, несёт `Behavior:
  contract|internal|wip`; сабжект `wip*` засчитывается как `Behavior: wip`; merge-коммиты освобождены.
- [#spec-trailer dump] Spec при contract: `Behavior: contract` требует трейлера `Spec: <путь>` ИЛИ изменения
  spec-файла капы в том же коммите — достаточно любого из двух.
- [#adhoc-body dump] Adhoc без файла: мелкое, уже обсуждённое решение (≤ 2 коммитов, та же территория, без
  открытых вопросов) живёт прямо в коммите — `Behavior: contract|internal` (+ `Spec:`), мини-променанс в теле
  сообщения; хук энфорсит непустое тело для contract без `Change:` (сабжект и трейлеры не считаются). Файл
  обязателен, когда работа длиннее, открывает новую территорию решений, спорна, трогает несколько капов или
  несёт открытые вопросы. Доля fileless contract — метрика дрейф-ревью.
- [#adhoc-id dump] Fileless-адхок обязан нести трейлер `Adhoc: <name>`: сообщения коммитов — это документ
  адхока, коммиты с одним именем складываются в один чейндж, имя может продолжать архивный чейндж (упущенное
  после факта). Кластер из ≥3 коммитов одного имени обязан стать файлом — `caped check push` помечает, тела
  переезжают в Provenance файла.
- [#idea-autonomy no-test dump] Агент спавнит идеи сам: человек решает «что», агент — «где живёт решение»
  (расширение чейнджа / новая идея / адхок — процедура в дампе, секция SPAWNING IDEAS); решение не должно жить
  только в чате и не должно дожидаться, пока человек скажет «это идея».
- [#territory-handoff no-test dump] Находка, адресующая контракт другой сущности (другого капа / идеи /
  чейнджа), передаётся сразу: правка секции Requirements цели + запись «handed off → <цель>» в променанс
  источника; обсудить и не передать = тихое откладывание = потеря; если цель должна лечь раньше — depends_on.
- [#idea-rename no-test dump] Ренейм идеи — один коммит: `git mv` + `name:` во фронтматере + все рефереры
  (`depends_on`, `spawned_from`, проза): рефереры — это контент ренейма, а не посторонние правки; сам файл
  меняется на строку, similarity держит `git log --follow`. Нового трейлера нет — событие выводимо из диффа;
  машинная проверка (совпадение `name:` с именем файла, висячие ссылки) — территория `caped check`, не хука.
- [#squash-legit no-test dump] Сквош чейнджа легитимен, но тогда променанс — единственная оставшаяся история
  шагов.

Дисциплина: атомарность (одно событие = один коммит; mv и архивацию не мешать с ПОСТОРОННИМИ правками —
дельты спек это и есть контент архивного коммита) и полнота
променанса (чат эфемерен — всё, что повлияло на решение, оседает в файле тем же коммитом).

Энфорсмент реализован в `scripts/hooks/commit-msg` (событийные проверки глобальны; все нарушения — события и
капы — собираются в один агрегированный репорт). Не энфорсится: стерильность mv (similarity 100%) — хук
проверяет факт rename, а не его чистоту; контентная валидация `spawned_from` — территория `caped check`;
содержательность тела adhoc-коммита — хук проверяет лишь его наличие.

### Трассировка требований и тестов

Требование и его машинная проверка связываются стабильными маркерами `[#<slug>]`; slug стабилен
(переформулировка требования не меняет slug, переименование — осознанное событие с правкой всех ссылок).
Trace видит только поставленные маркеры: требование, о котором забыли маркер, невидимо — полнота маркировки
держится формой секции ({#req-form}), а не эвристикой. Эвристика полноты (ворнинг на bold-lead буллеты без
маркера) снята чейнджем requirement-format: после стандартизации формы жирный лид — просто прозаическая
стилистика, а 9 из 9 её срабатываний на этом корпусе были ложными.

- [#req-form dump] Форма требования: требования enforced-спеки живут только буллетами внутри секции
  `## Requirements` (фиксированный английский литерал, не переводится), маркер первым —
  `- [#<slug>[ атрибуты]] Statement…` (мини-фронтматтер). Буллет без маркера внутри секции — ошибка
  `caped check`, как и маркерный буллет вне секции. Буллет самодостаточен: statement + ратионале рядом, не
  голый slug — иначе секция деградирует в write-only индекс, который проект отверг. `###`-группы и вводная
  проза внутри секции разрешены. Проверяется форма, не фразировка: состав предложения вне юрисдикции
  (SHALL-грамматика отвергнута). Ссылки требование→требование внутри спеки — `{#slug}` (фигурные скобки): не
  определение и не покрывающая цитата, `duplicate` не стреляет; рефы в тестах/коде остаются `[#<slug>]` и
  различаются с дефами классом файла. Первая строка буллета — самодостаточный гист, понятный без контекста:
  индекс требований (`caped render reqs`) показывает ровно её (продолжения не попадают; у legacy-буллетов,
  чья первая строка — точка переноса, индекс помечает обрыв «…»). В идеях и чейнджах секция та же, но форма
  мягче: только буллеты (нумерованные списки — ошибка `caped check`), slug опционален — требования идей
  эфемерны (умирают при архивации), стабильность слага им не нужна; если slug поставлен, он ведёт буллет,
  а ссылки на нормы из прозы — `{#slug}` (упоминания в бэктиках маркерами не считаются).
- [#trace-defs dump] Определения — slug-first буллеты с маркерами `[#<slug>]` в spec-файлах enforced-кап
  ({#req-form}); маркер, процитированный в прозе спеки вне такого буллета, определением не считается.
- [#trace-refs dump] Тест, покрывающий требование, повторяет тот же маркер у себя — в имени сценария или
  комментарии.
- [#trace-dump-attr dump] У маркера могут быть атрибуты внутри скобок, в любом порядке. `[#<slug> dump]` —
  требование агент-фейсинг и обязано быть отражено в дампе правил (`scripts/caped.sh`, bare-вызов): агент
  adopting-репы видит только дамп и AGENTS.md-стаб, правило, существующее только в README, для него не
  существует. Атрибуты независимы: процессное правило может быть `no-test`, но всё равно обязано в дамп.
  Атрибут ставит автор правила в момент написания — курация у человека/агента, полнота машинопроверяема.
  Набор атрибутов закрыт (`no-test`, `dump`): неизвестный атрибут ломает распознавание дефа и ловится
  `caped check`; `dump` — self-host-специфика (дамп — собственные правила тула, в adopting-репе атрибут
  не встречается), `no-test` универсален. Новый атрибут — осознанная смена нормы (чейндж), а не локальное
  изобретение; генерализация («атрибут X = цитата обязательна в файле Y») — при втором потребителе.
- [#trace-no-test dump] `[#<slug> no-test]` — явное освобождение требования от машинной проверки: отличает
  «не тестируемо» (процессные и языковые конвенции) от «забыли покрыть».
- [#trace-checker dump] `caped trace` — статический чекер без запуска тестов: определения — slug-first буллеты
  в spec-файлах enforced-кап реестра, ссылки — голые маркеры во всех tracked-файлах кроме spec-файлов и
  `ideas/`/`changes/`. Падения: `uncovered` (определение без ссылки и без `no-test`), `dangling` (ссылка без
  определения — тест пережил требование), `duplicate` (один slug определён дважды). Статусы прохождения
  (JUnit/отчёты раннеров) — поверх этого слоя, когда появится потребитель. Прогон trace — гейт перед
  архивацией чейнджа: красный trace блокирует архив (в этом репо — через `just test`).
- [#trace-undumped dump] `undumped` — определение с атрибутом `dump` ни разу не процитировано в дампе правил:
  ссылка в тесте это не закрывает.

### Структурная валидация (caped check)

- [#check-structure dump] `caped check` валидирует каждый файл `ideas/*.md` и `changes/*.md`: фронтматер
  обязателен (поля `name`, `summary`; `name` совпадает с именем файла), все базовые секции на месте
  (Why / Context / Requirements / Decisions / Rejected alternatives / Provenance / Open questions).
  Ошибка — это инструкция по починке (тот же паттерн, что у хука), exit 1 при любом нарушении.
- [#check-spawned-from dump] Контентный `spawned_from`: ссылка обязана резолвиться в живую
  (`ideas/`/`changes/`) или архивную (трейлер `Archives:` в истории гита) сущность, ренеймы склеиваются.

### E2E-оценка агент-фейсинг инструкций

- [#secretary-e2e] «Хорошо ли инструкция объясняет» доказывается не линтом, а поведением агента, который её
  читает. Харнесс `tests/secretary/e2e_instructions.py` спавнит настоящего LLM-агента (дешёвая flash-модель,
  OpenAI-совместимый API, один тул `bash`) в песочнице-репо: агент получает ровно то, что видит агент
  adopting-репы (AGENTS.md-стаб + дамп), и играет сценарий («находка в середине чейнджа», «ренейм идеи»);
  ассерты — по произведённым артефактам (файлы, трейлеры в `git log`, чистый rename по `git log -M`), не по
  прозе модели. Прогон дорогой и недетерминированный — за флагом `CAPED_EVAL=1` + `LLM_API_KEY`, в дефолтный
  `just test` не входит (skip); транскрипты — `tests/secretary/last-e2e/` (гитигнор). Каденция: по требованию,
  перед архивацией секретарных правок.

## Рассмотрено и отклонено/отложено

- **FUSE-маунт derived-файлов** — отклонён: потребитель view'шек — агент, CLI для него тот же read path
  (аналогия: `export-schema`); единственная польза (глазами в дереве IDE) закрывается `render`, позже —
  возможно, опциональный IDE-плагин, никогда ядро.
- **E2E-тесты в фича-модулях** — отложено: flow-harness (`tests/common`, макрос, правило одного макроса на
  файл) — shared infra, которая потянется за тестами; вместо переезда — зеркальные имена и ссылки из README.
- **Генерация спек из тестов** — отклонена: из тестов извлекается «что», но не «почему»; тесты как контракт
  работают без прозы поверх. Генерится только механический индекс.
- **Пер-лайновый променанс** — отклонён: убивает читаемость; гранулярность — требование.
- **Статус-флаги во фронтматере** — отклонены: флаг, который надо не забыть переключить, — гарантированный
  дрейф; состояние читается из гита.
- **Папки на идею/чейндж** — отклонены: всё в одном файле умещается; скрэтч умирает с чейнджом.
- **Архив как папка** — отклонён: материализованная копия того, что гит уже хранит; архив — derived view.
- **Валидация SHALL-грамматики (openspec-стиль)** — отклонена: проверяем структуру (фронтматер, секции), не
  формальную грамматику прозы.
- **Caped внутри kudach** — отклонено: отдельный тул, свой сервер; kudach — первый adopting-проект.

## Жизненный цикл проекта

0. **Бутстрап**: семенной коммит — корневой `README.md` (учредительный документ) + реестр + хуки. Семени
   позволено быть ручным. Для подключаемого репо — `caped init` (см. выше) с реестром, где всё `legacy`,
   дальше капабилити флипаются по одной.
1. **Рождение идей**: из корневого README и из работы; `spawned_from` во фронтматере — граф рождения выводим.
   **Агент спавнит сам**: человек решает «что», агент — «где живёт решение» (расширение чейнджа / новая идея /
   адхок — процедура в дампе, секция SPAWNING IDEAS); решение не должно жить только в чате и не должно
   дожидаться, пока человек скажет «это идея» ({#idea-autonomy}).
2. **Взятие в работу**: `git mv ideas/<name>.md changes/<name>.md` отдельным коммитом без кода.
3. **Работа**: contract-коммиты несут дельты README в себе; изменение продуктового инварианта — дифф корневого
   README. Рождение/сплит/мерж капабилити — чейндж, трогающий реестр; границы эволюционируют по мере боли.
   **Находки, рождённые внутри чейнджа**: правка того же артефакта/контракта, который чейндж создаёт —
   расширение этого же чейнджа (коммиты с тем же `Change:`, решения дописываются в его файл); новая территория
   решений — отдельная идея со `spawned_from` (коммит с `Change: <parent>` + `Idea: <child>`). **Отложенный
   скоуп — тоже находка**: кусок, вырезанный из чейнджа в середине («это потом»), оформляется идеей со
   `spawned_from` тем же коммитом, что и вырезание, — «отложили молча» означает «потеряли».
   **Ренейм идеи** ({#idea-rename}): один коммит — `git mv` + `name:` во фронтматере + все рефереры
   (`depends_on`, `spawned_from`, проза): рефереры — это контент ренейма, а не посторонние правки; сам файл
   меняется на строку, similarity держит `git log --follow`. Нового трейлера нет — событие выводимо из
   диффа; машинная проверка (совпадение `name:` с именем файла, висячие ссылки) — территория `caped check`,
   не хука.
4. **Финиш**: файл чейнджа удаляется Archives-коммитом; архив, план, индексы — views. Подвисших состояний нет:
   каждое состояние выводится из гита, «сделан, но не синкан» невозможно.

- «для таких адхок решений я бы вообще убрал файл — есть гит мессадж, где такие вещи можно расписывать
  подробнее; файлы больше нужны для больших вещей»
- «создай папку с тестами — это же реально всё по процессу получается, буквально на каждую идею нужен свой

- имя caped — выбор человека из предложенных вариантов

Додумано агентом (с основаниями):

- Принцип «кураторское пишется, производное выводится» — обобщение жалобы на синк (65 спек / 0 ссылок: у
  write-only слоя нет потребителя).
- Гранулярность: трейлеры per-commit, цитаты — в файле сущности (по истории: чейндж растянут на десятки
  коммитов, половина «Fixes» — per-commit цитаты дадут мусорную разметку).
- Дельты умирают как файлы; дельта = дифф README в contract-коммите (хук уже требует правку спеки в том же
  коммите — двухшаговый синк не нужен; именно он убивал openspec-спеки).
- Статус сущности из местоположения/гита, не из фронтматера; `Change:` обязателен только для `contract`,
  опционален для `internal`/`wip` (контракт без чейнджа — необсуждённое правило, багфикс не должен плодить
  церемонию; цена — internal-коммиты выпадают из реконструкции архива, приемлемо).
- Состояния legacy/declared/enforced (аналогия: expand-contract миграции); advisory-first роллаут и исключение
  web_version (по ретро-замеру: 7% подозрительных, концентрация в web).
- Бизнес-капы = записи реестра с глобами на доки (логика: капабилити — область решений; гиту всё равно, код в
  коммитах или нет); «идеи — глаголы, капы — существительные» (основание: newcomer — вопрос, пока нет стоячей
  стратегии; кап появляется с территорией решений).
- plan.md — исключение «in-place + коммитится» (единственный view, который человек читает чаще агента).
- Пилот фасадов на feed, разбор хелперов (по замеру 79/4 и 175/121).
- Шимы навсегда + latency хука (git-хуку нужен исполняемый файл; цена платится на каждый коммит).
- Секция «Рассмотрено и отклонено» как обязательная часть идеи (основание: цитата человека про «второй раз по
  кругу»; e2e-ко-локация и спеки-из-тестов уже всплывали по разу за этот диалог).
- Событийные маркеры в трейлерах: `Idea:` на коммите рождения, `Change:` на spawn-коммите несёт двойную
  семантику (он и так часть патчсета чейнджа — отдельное поле «откуда родилась» не нужно, durable-связь живёт во
  `spawned_from` фронтматера, переживающем сквош).
- mv взятия в работу — чистым коммитом (основание: порог similarity rename detection; смешанный с правками mv
  рвёт `git log --follow` на два файла).
- Атомарность событий и «чат эфемерен, променанс — нет» (следствие цели «вся работа восстановима из гита»:
  единственный долговечный носитель «почему» — файл сущности в том же коммите).
- Правила — в CLI, не в AGENTS.md (аналогия: `bd prime` из beads — единственный известный прецедент
  rules-in-CLI; контраст: OpenSpec держит правила в маркдауне, и по истории kudach write-only слои без
  потребителя дрейфуют). AGENTS.md — стаб-указатель; диспетчер v0 сразу несёт все подкоманды и финальную форму
  шима, чтобы мышечная память агентов не менялась при появлении check/render и бинаря.
- Слепой тест (сабагент, только AGENTS.md + bare-вывод): понимание ~80%; найденные дыры — дамп не отправляет
  читать реестр, противоречие «архивация без контента» vs «архив применяет дельты», тройное прочтение `Spec:`,
  неоговорённый `Behavior:` на архивном коммите, молчание про идемпотентность init, свободные phase/priority.
  Всё это — правки текста дампа в рамках того же чейнджа (правило «расширение vs новая идея» применено к себе).
- Правило «расширение vs новая идея»: граница — тот же контракт или новая территория решений (основание: иначе
  каждая итерация полировки плодит микро-идеи, а размазывание новой территории по чужому чейнджу рвёт
  реконструкцию «почему»).
- Fileless-адхок почти не требует кода: хук уже не требует файл без `Change:`-трейлера; единственный новый
  энфорс — непустое тело contract-коммита (контент тела непроверяем хуком — граница «хук vs совесть», как со
  спеками); порог «когда файл обязателен» — количественное правило, отдано дрейф-ревью, а не хуку (ложные
  срабатывания на легитимных цепочках хуже пропуска). Полировка хука (longest-prefix-wins, агрегированный
  репорт, single-commit финиш) вошла расширением в тот же чейндж — правило применено к себе.
- Трассировка требование↔тест стабильными маркерами `[#<slug>]`. Человек: «Хотя бы на уровне названия
  требований, иначе точно разъедутся рано или поздно» и «У нас откуда ща требования брать, в ридми их просто
  перечислить?» Додумано агентом (с основаниями): маркеры инлайн в прозе буллетов, а не отдельным списком
  (основание: отдельный индекс требований — write-only слой, дрейфует; инлайн-маркер умирает вместе с
  предложением при правке); `[#<slug> no-test]` — явное освобождение, чтобы отличать «не тестируемо» от «забыли
  покрыть»; чекер статический (git ls-files + grep, без JUnit на v0) — основание: название и статус теста
  системе плагинов отдали бы минимум, но язык проекта неизвестен, а grep универсален; ретро-маркировка
  существующих буллетов и суффиксы к именам сценариев — в том же чейндже (та же территория контракта).
- Автономный спавн идей агентом. Человек: «человек принимает решения, а агент корректно сам идеи
  спавнит/меняет когда надо, чтобы не я говорил, что это должно быть идеей, а агент из инструкций сразу это
  понимал нормально». Додумано агентом: процедура живёт в дампе отдельной секцией SPAWNING IDEAS (основание:
  дамп — единственное, что агент гарантированно читает; README несёт норму + променанс), а секция
  «Рассмотрено и отклонено» поднята из променанса в обязательный набор секций идеи (была зафиксирована как
  решение, но в контракт формата не попала — дыра именно того типа, про который вопрос).

## Открытые вопросы

- Гранулярность энфорсмента: per-commit (v0) vs per-push — wip-коммиты не должны драться с хуком.
- Формат и место реестра: для v0 решено — `caped.registry` у корня, плоский TAB-формат
  `name⇥path-prefix⇥state⇥spec-file` с prefix-матчем (shell-парсабельно без зависимостей, diff-френдли).
  YAML/дерево/вложенность — вопрос v0.1, когда появится второй adopting-проект.
- Установка хуков в `caped init`: шимы в `.git/hooks` (переживают clean, не версионируются) vs
  `core.hooksPath` на caped-managed каталог (версионируемость vs хрупкость при clean).
- ~~Дрейф-ревью: периодический агент-прогон vs команда по требованию~~ — стало идеей `history-sweep`:
  периодический агент-аудитор поверх view-слоя, advisory.
- Фасады — в этой идее или отдельной: требование ортогонально.
- Валидация rename `ideas/` → `changes/` хуком — решено: да, входит в событийный энфорсмент (см. «События
  жизненного цикла»); реализация — следующая итерация хука.
- Место бизнес-капов: `caps/` vs `biz/` vs docs-поддерево — деталь, но лучше решить до первого adopting-PR.
