# caped — доки и трекер, принадлежащие капабилити

## Зачем

Убрать пост-фактум ритуал синка `openspec/specs` и заодно ручные index/plan/archive. Модель: **одна сущность,
три состояния** — идея (`ideas/<name>.md`), чейндж (`changes/<name>.md`), архив (файл удалён Archives-коммитом;
состояние выводится из гита, не хранится). Каждая капабилити — кодовая, техническая или бизнесовая — имеет живой
README рядом со своими файлами. Свежесть обеспечивают машинерия, а не дисциплина: класс изменения в каждом
коммите (трейлеры, проверяемые хуком) и производные view (индекс идей, план, архив, история фичи, индекс
тестов), которые генерятся тулом, а не ведутся руками. Кураторское (ратионале, приоритеты, решения) пишется в
файлах; решения человека отделены от додумок агента — с основаниями, чтобы додумки можно было перепроверять и
не ходить по кругу второй раз.

Имя: **caped** («capability-ed»; коллизии проверены: capstan — AI-гавернанс, codicil — npm memory-ledger,
capstone — дизассемблер; у caped тёзка только из биомеда). Этот файл — корневой README тула и его учредительный
документ, по собственной модели: проект как корневая капабилити.

## Контекст

  Принято предупреждение поля: машинно-сгенерированный контекст вредит — генерятся только механические индексы.

## Требования

### Одна сущность, три состояния

Идея и чейндж — один файл одного формата: YAML-фронтматер (`name`, `summary`, `phase`, `priority`,
`depends_on`, `spawned_from`) + проза + променанс. Статус не хранится — выводится: файл в `ideas/` = идея, в
`changes/` = в работе, удалён из `changes/` = архив (дата = дата Archives-коммита). Папок под сущность нет;
скрэтч-материалы большого чейнджа кладутся рядом и умирают при удалении. Параллельные чейнджи на одной ветке
различаются трейлером `Change:`.

### Формат идеи/чейнджа

Секции идеи: Зачем / Контекст / Требования / Променанс / Открытые вопросы. Секции чейнджа: Зачем / Решения
(с променансом) / Открытые вопросы / Задачи. `caped check` валидирует фронтматер и наличие секций (входит в
verify) — это замена openspec-валидации SHALL-грамматики: проверяем структуру, не формальность. Правило
промоушна вопросов: мелкий открытый вопрос отвечается прямо в чейндже и умирает с ним; вопрос, ставший работой,
промоутится в идею (`spawned_from` фиксирует происхождение).

### Реестр капабилити (адресуемость)

Машиночитаемый реестр: имя → глобы путей → spec-файл → состояние `legacy | declared | enforced`. Корень дерева —
проект как одна большая фича: корневой `README.md` играет роль README капабилити; README отвечает «что и
зачем», AGENTS.md — «как работать», не дублируются. Неперечисленные пути тул игнорирует by design — это путь
переезда: капабилити вводится одним PR, репорт показывает покрытие.

Капабилити — область решений, не обязательно область кода. **Технические капы** (shared-слои `entities/`,
`platform/`, `app/`) имеют свои README с техническими инвариантами (детерминизм, паттерны граф-рёбер) — это
настоящий дом того, что сейчас размазано по AGENTS.md; `Spec:` на их contract-коммитах обязателен.
**Бизнес-капы** (marketing, acquisition, монетизация) — записи с глобами на свои доки (`caps/marketing/**`),
spec-файл — стоячее содержимое области (стратегия, инварианты «пользователи платят, организаторы бесплатно»,
break-even расчёты). Хук работает и там: правка `caps/marketing/README.md` — это `Behavior: contract` (смена
стратегии → нужен чейндж) или `internal` (уточнение формулировки); механический гейт «бизнес-решение проходит
через человека» — тот же механизм, что CODEOWNERS, только бесплатно. Различие «идея vs кап»: идеи отвечают на
вопросы (глаголы), капы владеют территорией (существительные); идея становится капом, когда появляется стоячая
область решений. Прогон: `ideas/newcomer-acquisition.md` → чейндж-исследование → дельта корневого README +
рождение капа `acquisition` (`caps/acquisition/README.md`) + спавн кодовых идей (лендинг под туристов) →
Archives-коммит, ни одной строчки кода.

### Декларированные классы изменений

Коммит, трогающий код `enforced`-капабилити, несёт `Behavior: contract | internal | wip`; у `contract` —
дополнительно `Spec: <путь>` или правка spec-файла в том же коммите (для cross-cutting — `Spec: README.md`).
У `contract`-коммитов трейлер `Change: <name>` обязателен (контракт без чейндж-документа = необсуждённое
бизнес-правило); у `internal`/`wip` — опционален (багфикс не плодит церемонию; хотфикс контракта = чейндж-файл
+ код + дельта README одним коммитом). Хук проверяет существование `changes/<name>.md` по staged-дереву.
Сообщения хука пишутся так, чтобы агент чинил коммит сам, без человека. Энфорсит versioned commit-msg хук
(`core.hooksPath`). Роллаут: advisory → блокировка после калибровки; web_version — кандидат на временное
исключение до web-e2e.

### README капабилити рядом с её файлами

`src/features/<cap>/README.md` (или `caps/<cap>/README.md`): зачем, текущие инварианты, ссылки на архивные
чейнджи. Пишется агентом в момент чейнджа из слов человека; изменение README — бизнес-изменение, аппрувится
человеком по диффу, поэтому README обязан быть достаточно мал, чтобы дифф реально читался. `openspec/specs/`
замораживается read-only; миграция ленивая — README появляется при следующем касании. `docs/` остаётся только
для искренне cross-cutting нарративов; per-feature содержимое уходит в README капов. Дельт-файлов в чейндже
нет: дельта — это дифф README внутри contract-коммита, атомарно и ревьюабельно.

### Променанс решений

Идеи и чейнджи различают решения человека (дословные цитаты) и додумки агента (с основанием: логика / аналогия).
Додумка с записанным основанием перепроверяема: дрейф-ревью прогоняет вывод заново и помечает правила, чьё
основание перестало держаться. Гранулярность — требование, не предложение. Полный список рассмотренных
альтернатив хранится в файле идеи (см. ниже) — это страховка от повторного хождения по кругу.

### Производные view

Из фронтматера и гита тул рендерит по запросу: индекс идей, план (по `phase`/`priority`/`depends_on` — граф, а
не дрейфующая проза; `depends_on` — гейт: нельзя в работу, пока зависимость не архивирована), архив чейнджей
(`change show` достаёт док из истории + все его коммиты по `Change:`-трейлеру), историю фичи
(`git log --follow` + фильтр по трейлерам), индекс тестов (doc-комменты + имена fn; тесты остаются в
`tests/e2e/` с зеркальными именами, README капа ссылается на них). `caped materialise` вываливает всё в
`.caped/` для просмотра глазами; закоммитить нельзя (`.gitignore` + pre-commit проверка staged путей под
`.caped/`, ловит `git add -f`). Исключение: `plan.md` генерится in-place и коммитится (его человек читает чаще
агента), свежесть сторожит verify; исключение задокументировано как исключение.

Дрейф-ревью — эволюция ретро-репорта: сопоставление декларированного (`Behavior`-трейлеры) против фактического
(диффы). Существующий `openspec/changes/archive/` не трогаем: легаси-датасет для реконструкции и готовый
golden-корпус для `change show`.

### Веб-UI (поздняя фаза)

Тот же derived view, но live-рендер. caped — отдельный инструмент, не часть kudach, со своим сервером; веб-UI —
страницы плана/чейнджей/истории там, возможное место глазного аппрува README-диффов. CLI первым (его
потребитель — агенты), веб вторым.

### Фасады (пилот)

В принятых капабилити mod.rs объявляет сабмодули приватными, наружу — явные `pub use`. Задуманные поверхности
(`commands`, `workflow`, `mcp`, `telegram`) — фасад по умолчанию. Пилот на `feed`; судьба хелперов
(`categories`, `formatting` — публичная точка feed или переезд в platform/) решается по замерам пилота.

### Сам тул — по своей же схеме

v0 — существующие шелл-скрипты (бутстрап-семя, пишется руками). v0.1 — однобинарный CLI; шелл-скрипты
становятся шимами `exec caped hook commit-msg "$@"` навсегда (git-хуку нужен исполняемый вход). С v0.1 репо тула
живёт по своей схеме — догфудинг как постоянный e2e; его капабилити: hook, registry, index-gen, report,
web-ui. Хук обязан быть быстрым: bash/rust-класс старта. Первый adopting-проект — kudach: PR с реестром, где
всё `legacy`, advisory-режим, первая enforced-капабилити — feed (там же фасадный пилот).

## Рассмотрено и отклонено/отложено

- **FUSE-маунт derived-файлов** — отклонён: потребитель view'шек — агент, CLI для него тот же read path
  (аналогия: `export-schema`); единственная польза (глазами в дереве IDE) закрывается `materialise`, позже —
  возможно, опциональный IDE-плагин, никогда ядро.
- **E2E-тесты в фича-модулях** — отложено: flow-harness (`tests/common`, макрос, правило одного макроса на
  файл) — shared infra, которая потянется за тестами; вместо переезда — зеркальные имена и ссылки из README.
- **Генерация спек из тестов** — отклонена: из тестов извлекается «что», но не «почему»; тесты как контракт
  работают без прозы поверх. Генерится только механический индекс.
- **Пер-лайновый променанс** — отклонён: убивает читаемость; гранулярность — требование.
- **Статус-флаги во фронтматере** — отклонены: флаг, который надо не забыть переключить, — гарантированный
  дрейф; состояние читается из гита.
- **Папки на идею/чейндж** — отклонены: всё в одном файле умещается; скрэтч умирает с чейнджом.
- **Архив как папка** — отклонён: материализованная копия того, что гит уже хранит; архив — derived view.
- **Валидация SHALL-грамматики (openspec-стиль)** — отклонена: проверяем структуру (фронтматер, секции), не
  формальную грамматику прозы.
- **Caped внутри kudach** — отклонено: отдельный тул, свой сервер; kudach — первый adopting-проект.

## Жизненный цикл проекта

0. **Бутстрап**: семенной коммит — корневой `README.md` (учредительный документ) + реестр + хуки. Семени
   позволено быть ручным. Для существующего репо — PR с реестром, где всё `legacy`, дальше по одной капабилити.
1. **Рождение идей**: из корневого README и из работы; `spawned_from` во фронтматере — граф рождения выводим.
2. **Взятие в работу**: `git mv ideas/<name>.md changes/<name>.md` отдельным коммитом без кода.
3. **Работа**: contract-коммиты несут дельты README в себе; изменение продуктового инварианта — дифф корневого
   README. Рождение/сплит/мерж капабилити — чейндж, трогающий реестр; границы эволюционируют по мере боли.
4. **Финиш**: файл чейнджа удаляется Archives-коммитом; архив, план, индексы — views. Подвисших состояний нет:
   каждое состояние выводится из гита, «сделан, но не синкан» невозможно.

## Откуда что взялось (променанс)

Решения человека (дословно):

- «папка с идеями/планом как адхок ишшу трекер это прям хорошо, а спеки как будто сбоку болтаются»
- «мб спеки должны лежать в фича модулях просто? Как ридми условно»; «собирать спеки из описания тестов»
- «у агента должна быть актуальная история изменений и набор требований без того чтобы лазить в тесты»;
  «ратионале должен в спеке плейнтекстом лежать»
- «современные агенты прекрасно понимают мои сумбурные мысли и нормально их раскрывают»
- «пишем чейндж в кратком машиночитаемом формате прям в гит мессадж и проверяем гит хуком»
- «индекс чуть ли не через fuse, чтобы файлы by design были ридонли»; «может быть отдельным плагином просто»
- «путь переезда надо предусмотреть, чтобы капабилити вводились по очереди, а непокрытые тул игнорил»
- «сам тул надо по такой же схеме делать сразу; бутстрап — эти несколько шелл скриптов на хуках?»
- «склоняюсь к self-contained фичам, общающимся через публичный интерфейс mod.rs / index.ts»
- «итог чейнджа — пачка коммитов, файл чейнджа пропадает в последнем коммите, достать через caped; архив в коде
  не несёт ценности, если он в гите есть»
- «если всё в одном файле, то идеи отдельными папками не нужны, пусть файлами будут»; «индекс идей должен
  автоматом рендериться через frontmatter»; «план бы тоже формализовать»
- «можно веб-интерфейс прикрутить, чтобы план/таски смотреть в красивом виде — тогда материализовывать не надо»
- «корневой ридми — это корневой кап, проект как одна большая фича»
- «как идея берётся в работу — делаешь mv idea→change, и хук уже видит, что чейндж в работе»
- «цикл: корневой ридми с описанием проекта → из него рождаются идеи → идут в работу → генерят новые идеи и
  меняют существующие капы, включая корневой файл»
- «spec на shared-слоях — тоже важные вещи, просто технические, а не бизнесовые»; «кросскаттинг-штуки точно
  стоит проводить через чейндж»
- «есть идеи чисто бизнесовые, которые в коде не отражаются, типа newcomer»; «это ж получается marketing
  капабилити, просто не в src лежит?»
- «там вся история решений по идее должна быть, чтобы ничего не забыли или второй раз по кругу не ходили»
- имя caped — выбор человека из предложенных вариантов

Додумано агентом (с основаниями):

- Принцип «кураторское пишется, производное выводится» — обобщение жалобы на синк (65 спек / 0 ссылок: у
  write-only слоя нет потребителя).
- Гранулярность: трейлеры per-commit, цитаты — в файле сущности (по истории: чейндж растянут на десятки
  коммитов, половина «Fixes» — per-commit цитаты дадут мусорную разметку).
- Дельты умирают как файлы; дельта = дифф README в contract-коммите (хук уже требует правку спеки в том же
  коммите — двухшаговый синк не нужен; именно он убивал openspec-спеки).
- Статус сущности из местоположения/гита, не из фронтматера; `Change:` обязателен только для `contract`,
  опционален для `internal`/`wip` (контракт без чейнджа — необсуждённое правило, багфикс не должен плодить
  церемонию; цена — internal-коммиты выпадают из реконструкции архива, приемлемо).
- Состояния legacy/declared/enforced (аналогия: expand-contract миграции); advisory-first роллаут и исключение
  web_version (по ретро-замеру: 7% подозрительных, концентрация в web).
- Бизнес-капы = записи реестра с глобами на доки (логика: капабилити — область решений; гиту всё равно, код в
  коммитах или нет); «идеи — глаголы, капы — существительные» (основание: newcomer — вопрос, пока нет стоячей
  стратегии; кап появляется с территорией решений).
- plan.md — исключение «in-place + коммитится» (единственный view, который человек читает чаще агента).
- Пилот фасадов на feed, разбор хелперов (по замеру 79/4 и 175/121).
- Шимы навсегда + latency хука (git-хуку нужен исполняемый файл; цена платится на каждый коммит).
- Секция «Рассмотрено и отклонено» как обязательная часть идеи (основание: цитата человека про «второй раз по
  кругу»; e2e-ко-локация и спеки-из-тестов уже всплывали по разу за этот диалог).

## Открытые вопросы

- Гранулярность энфорсмента: per-commit (v0) vs per-push — wip-коммиты не должны драться с хуком.
- Формат и место реестра: YAML у корня vs секция в существующем конфиге; дерево с корнем или плоский список +
  особый root-вход.
- Дрейф-ревью: периодический агент-прогон (каденция?) vs команда по требованию.
- Фасады — в этой идее или отдельной: требование ортогонально.
- Валидация rename `ideas/` → `changes/` хуком: стоит ли на старте, или лишняя строгость.
- Место бизнес-капов: `caps/` vs `biz/` vs docs-поддерево — деталь, но лучше решить до первого adopting-PR.
